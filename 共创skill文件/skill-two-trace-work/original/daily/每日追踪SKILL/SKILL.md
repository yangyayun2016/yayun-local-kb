# ASIN 每日竞争追踪

每天一次，把自有产品和竞品的关键运营指标拉下来，和昨天比，只报有意义的变化，让卖家十秒看完该看的，省掉每天手动搜词、逐个翻链接的重复劳动。

这套工具的价值在**判断逻辑**（什么变化值得报、谁和谁是竞品、怎么管住数据额度），不在取数本身。取数可以用卖家精灵 MCP，也可以手动喂——判断框架是一样的。

## 数据来源：两种模式（首次让用户选）

**模式 A · 卖家精灵 MCP（推荐，自动）**
用户已连接卖家精灵 MCP 时，AI 直接调 asin_detail 拉数据。每个 ASIN 一次调用。

**模式 B · 手动喂数（无 MCP 时的兜底）**
没有卖家精灵或同类数据 MCP 的用户，每天自己从任意工具（卖家精灵网页端、Helium10、亚马逊前台等）复制各 ASIN 的 BSR、评分、评分数、价格、Buy Box 卖家，贴给 AI。AI 用**完全相同的异动判断、竞争分组、报告逻辑**处理。效果取决于用户喂的数据，但分析框架不打折。

> 不内置爬虫脚本：亚马逊前台有反爬与验证码，自抓数据不稳、易失效、需要买家自己维护代理，且本 skill 以纯文档工作流分发。取数请用 MCP 或手动，不要让 AI 去爬前台。

## 重要前提

半自动工具，不是无人值守的定时任务：用户每天说一句"跑今天的追踪"触发。想定时就自己设个每日提醒。

## 卖家精灵配额纪律（用模式 A 时，首次设定必须提醒）

卖家精灵 MCP **每调用一次接口消耗一次额度**（指定返回字段能省 token，但不省调用次数）。这是模式 A 最硬的约束：

- 常见套餐 1000 次/月，平摊约 33 次/天。
- 一次追踪消耗 = 自有 ASIN 数 + 竞品 ASIN 数（每个 ASIN 调一次 asin_detail）。
- 所以每天追踪的 ASIN 总数 ≈ 每天消耗次数。要留余量给临时的选品/关键词调研，**建议每日追踪 ≤ 5 个 ASIN**（如 2 自有 + 3 竞品 = 5 次/天 ×30 天 = 150 次/月，很安全）。
- 首次配置时按用户填的 ASIN 数当场算账："你这样是 X 个 ASIN，每天 X 次，月约 30X 次，占 1000 次的百分之几，其余够不够调研。" 太多就提醒砍。

**本地配额记账**：卖家精灵 MCP 没有查余额的接口，AI 读不到真实剩余次数。替代做法是本地记账（见下方 quota_tracker 模板）：每跑一次把本次调用数加上去，月初手动归零，接近上限时在报告末尾提醒。这是估算，和后台真实余额有偏差（用户在别处的调用算不到），仅防"追踪本身把额度跑爆"。

## 竞争组：谁和谁是竞品

ASIN 一多、且分属不同类目时，必须知道哪个竞品对应哪个自有产品，否则会拿不相干的两个产品瞎比。配置按竞争组组织，每组 = 一类自有产品 + 它的对应竞品。**报告按组出，组内才比较，不跨组比。**

确定配对，按可靠性优先级：

1. **卖家手动指定（最优先）**：竞品标注它对应哪些自有 ASIN。有手动指定就以它为准，不被自动判断覆盖。
2. **类目节点粗筛**：用 asin_detail 的 nodeIdPath。**父节点（路径前段）不同的基本不是竞品**，可排除。但**不要拿叶子节点（末段）当唯一标准**——同种产品常分属不同叶子节点（例：同一种小商品可能一个挂在「A 大类 > 子类甲」、一个挂在「A 大类 > 子类乙」，父节点相同、叶子不同，但实为直接竞品）。类目只用于粗筛排除明显不相干的。
3. **产品名/标题细判（兜底）**：粗筛通过后用 title 关键词判断是否同品。最弱、易误判，仅在无手动指定时用。

自动归组的竞品在报告里标"（自动配对，待确认）"，让卖家一句话确认或纠正；确认后写回配置，下次不再猜。归不进任何组的，单独列出来问卖家。

## 行动标记：自动侦测"动作型"变化，7 天内挂进报告

排名、转化的变化往往是几天前某个动作（调价、上 coupon、加变体等）的滞后结果。隔两天再看报告，很容易忘了"这产品最近排名往上走，前几天它是不是降过价"。本 skill 在每天取数比对时，**自动从数据里侦测出"动作型"变化**，记一条带日期的标记到 `actions_log.json`，并在动作发生后 **7 天内**的每份报告里把它挂在对应产品行下，作为解读变化的背景。

**关键定位（务必说清，别夸大）**：
- 这是**从 asin_detail 数据里自动侦测**，不是手动登记，也不是你后台操作的记录。能侦测的范围 = asin_detail 取得到的字段；像"开新广告""站外引流""改主图内容"这类数据看不到的动作，侦测不到。报告里只说"数据上看到的动作"，不假装知道全部。
- **自有和竞品都标**。自有产品的动作帮你回忆自己做了什么；竞品的动作就是对手的可见操作。
- **7 天窗口**默认值，配置里 `action_window_days` 可改。窗口外的标记不再挂出，但仍留文件备查。

**哪些变化算"动作"（有明确起点、可视为一次操作）——自动落库**：
- **调价**：价格出现变动（沿用异动阈值 ≥ $0.5 或 ≥ 5%）。记"调价 $28.99→$26.99"。
- **coupon 上/撤**：coupon 从无到有或从有到无。
- **变体增减**：variations/skuList 数量变化。
- **Buy Box 易主**：sellerName 变化。
- **AC/BS 标得失**：badge.amazonChoice / badge.bestSeller 得到或失去。
- **评论数异常**：单日新增 ≥ 50，或出现下降。这类**措辞必须留余地**——记"评论数单日 +63（异常，关注是否买评/站外/促销）"，**不直接断定刷单**；观测到的只是数字异常，成因有多种可能，判断权留给用户。

**哪些不算动作（连续型波动，不落库，只在当日异动报告里照常报）**：BSR、评分值、评论数的常规小幅波动。这些没有明确"起点"，当成动作会污染记录。

**侦测口径**：动作侦测复用第 4 步的"今天 vs 上一条"比对结果——凡比对中检出上述类型的变化，就在写历史的同时往 actions_log.json 追加一条。同一动作只在发生当天记一次，不每天重复记。

## 每日执行流程

1. 读取配置（首次按下方模板生成 tracker_config.json），遍历竞争组。
   - **显示名**：优先用手填的 label（通常是后台自编 SKU，最好认）；为空用 fallback_label。报告和历史一律用显示名，不只甩 ASIN。卖家精灵抓不到后台自编 SKU，label 只能手填。
   - 按"竞争组"优先级确认每个竞品对应哪些自有产品。
2. **取数**：模式 A 对每个 ASIN 调一次 asin_detail（按 return_fields 取字段），记下本次调用数；模式 B 让用户贴入当日数据。
3. 读历史记录，取每个 ASIN 最近一条作对比基线。
4. 比对今天 vs 上一条，生成异动报告（含 AI 分析，见下）。比对中**凡检出"动作型"变化**（调价 / coupon 上撤 / 变体增减 / Buy Box 易主 / AC·BS 标得失 / 评论数异常），同步往 `actions_log.json` 追加一条带日期的标记。
5. 读 `actions_log.json`，筛出今天往前 `action_window_days`（默认 7）天内、且对应本次追踪 ASIN 的活跃标记，挂进报告对应产品行、并供 AI 分析引用。
6. 把今天数据追加写入历史（一个 ASIN 一行，带日期）。
7. 模式 A 下更新配额记账，接近上限则提醒。

> 读写 actions_log.json 不调任何卖家精灵接口，**不消耗额度**。模式 B（手动喂数）下，只要用户贴的数据里含价格/coupon/变体等字段，同样能侦测并标记。

## 异动判断（什么算"值得报"）

只报达到阈值的变化，其余一句"其他指标无明显变化"带过：

- **BSR**：大类排名变化 ≥ 10%，或小类排名变化 ≥ 3 名 → 报。BSR 数字越小越好，数字变大是负面。
- **价格**：自有或竞品价格变化 ≥ $0.5 或 ≥ 5% → 报。竞品降价尤其要点出来。
- **评分数**：单日新增 ≥ 20，或出现下降 → 报。
- **评分**：变化 ≥ 0.1 → 报（评分掉了要警觉，可能来了差评）。
- **Buy Box 卖家变化**：自有产品 Buy Box 易主 → 高优先级报（可能被跟卖）。
- **Amazon's Choice 标**（仅用户开启时）：得到或失去 → 报。

> 阈值是通用默认值。用一段时间后按自己类目的日常波动幅度校准——有些类目 BSR 天然天天大幅跳，10% 就太敏感。

## 报告格式

简短，先结论再细节。用 Markdown 表格 + 统一符号呈现，让卖家扫一眼就抓到涨跌方向。多组时按组分段，组内才做自有 vs 竞品对比，不跨组比。

**统一符号约定**（每份报告固定，不临时换）：
- 🟢 = 对"我"有利的变化（自有排名升、评分升；竞品涨价、排名跌、评分掉等）
- 🔴 = 对"我"不利或需警觉（自有排名跌/评分跌/被跟卖；竞品降价、评分数暴增、冲排名等）
- `—` = 该指标无明显变化（已看过、没动，不是缺数据）
- 箭头表方向：**BSR 按"名次升降"标，不按数字增减标**——BSR 数字变小=排名上升=显示 ↑（这是最易标反的地方，务必按名次方向标）；价格、评分、评分数用实际增减值（如 ↓$1.20、+24、↓0.2）

报告结构：

### 1. 今日重点
跨所有组，1–3 条最该注意的，每条带 🔴/🟢 前缀。没有就写"今日无重大异动"。

### 2. 按竞争组分段
每组一张表，列出组内自有 + 竞品的当前值与变化。**只在达到异动阈值的变化项上加箭头和符号，无变化的列一律填 `—`**（避免满屏标记反而失焦）：

| 产品 | 角色 | BSR(大类) | 评分 | 评分数 | 价格 | Buy Box |
|------|------|-----------|------|--------|------|---------|
| A简称 | 自有 | 1,240 ↑8% 🟢 | 4.6 — | 312 (+5) | $26.99 — | 你 |
| B简称 | 竞品 | 980 ↓3% 🔴 | 4.5 — | 890 (+24) 🔴 | $24.79 ↓$1.20 🔴 | 第三方 |

**活跃动作挂载**：若某产品（自有或竞品）在 7 天窗口内有侦测到的动作标记，在它那一行下方挂一行（不占表格列，写成表下小字注脚）：

> 📌 A简称 · 近期动作：3 天前调价 $28.99→$26.99；昨天上 5% coupon。
> 📌 B竞品 · 近期动作：5 天前评论数单日 +63（异常，关注是否买评/站外）。

只挂窗口内的；没有动作的产品不挂、不写"无动作"占行。

表下接**组内 AI 分析**（不只复述数字，见下节），再接一句话竞品提示。

### 组内 AI 分析（结合最近动作）
每组在表与动作挂载之后，给一小段（2–4 句）AI 分析，把**本组的数值变化**和**7 天窗口内的活跃动作**放在一起读，回答"这周这组在发生什么、值不值得管"。要求：

- **把变化和窗口内动作对起来读**：如"自有 A 的 BSR 这两天回升，时间上和 3 天前那次降价对得上"；或"竞品 B 评论数 5 天前异常 +63，这两天它 BSR 在上冲，时间上对得上，留意是不是在催量"。
- **归因必须留余地**：用"时间上吻合 / 可能相关 / 对得上"，**不要**写成"因为降价所以排名升"——观测不到因果，只看到先后。评论数异常更要克制，写"关注是否买评/站外"，不直接定性刷单。把判断权留给用户。
- **没有动作可解释时**就直说变化是外部的（竞品、类目大盘、季节），别硬往动作上套。
- **没动作、也没异动**的组，一句"本组无明显变化，无近期动作"带过，不强行分析。
- 冷静、不渲染，信息不足就说"信息不足，建议自己看一眼"。

### 3. 待确认配对
自动配对未确认的竞品，标"（自动配对，待确认）"，请卖家一句话确认或纠正。确认后写回配置，下次不再猜。

### 4. 配额提醒
仅模式 A 且接近上限时出现。

单组时不必强行分段，直接出表 + 今日重点即可。

> 显示名用配置里的 label/fallback_label，不要在表里只甩 ASIN。

## 异动升级 → 深挖竞品衔接（与 competitor-monitor skill 打通）

日常异动报告只回答「竞品动了」。当某竞品的变化大到值得追问「它到底改了什么」时，本 skill 不自己分析 listing 细节（那是 competitor-monitor skill 的活），而是在报告末尾**点用户一下、给出一句话触发**，由用户决定要不要深挖。

**升级阈值**（比日常报告阈值更严，避免天天提示）：满足任一即触发升级提示
- 竞品大类 BSR 单日变化 ≥ 25%（日常报告阈值是 10%）
- 竞品降价 ≥ 10%，或新上/撤下 coupon
- 竞品评分数单日新增异常高（远超日常 +20 的量级，如 +50 以上）
- 竞品 Buy Box 卖家易主，或跟卖数明显增加

**触发时**，在报告「今日重点」或对应竞争组末尾追加一行：

> ⚠️ **[竞品简称]** 异动较大（具体：如"大类 BSR 升 31% + 新上 coupon"）。想知道它具体改了什么，回复 **「深挖 [竞品简称]」**。

用户回「深挖 X」→ 转入 competitor-monitor skill，对该竞品跑一次 listing 快照比对。

**报告固定带一行衔接提示**：无论本次有没有竞品达到升级阈值，报告末尾都固定出现一行竞品监控衔接，让两个 skill 始终连着、用户随时知道下一步在哪：

- **有竞品达到升级阈值时**：点名最值得的 1–2 个，如
  > 🔗 下一步：**[竞品简称]** 本次异动较大，建议深挖它改了什么 → 回复 **「深挖 [竞品简称]」**。
- **没有竞品达到升级阈值时**：给中性的常规衔接，不制造焦虑，如
  > 🔗 下一步：今日无竞品达到深挖阈值。想主动查某个竞品 listing 改动，回复 **「深挖 [竞品简称]」** 或 **「监控竞品变动」**（跑全部竞品）。

**重要边界**：
- 这是**建议 + 用户确认**，不是自动执行。深挖要额外调 asin_detail、消耗额度，不在用户不知情时自动花掉——与本 skill「半自动、用户触发、不无人值守」一致。固定衔接行只是"提示入口"，不替用户花额度。
- 点名升级的竞品最多 1–2 条，挑最值得的，不每个竞品都点，避免麻木。
- 衔接行固定出现，但**点名升级**只在真有竞品超阈值时才有；没有就走上面的中性版本，不强行制造「值得深挖」的假象。

## 竞品 ASIN 初次录入引导（初始化 competitor-monitor）

竞品监控靠快照比对，**文字/结构型字段（标题、五点、变体、AC标、主图）没有历史、只能从首次记录那天起算**。所以越早给竞品建基线越好——不建，对手现在改了什么日后就永远比不出来。

**触发时机**：当用户**首次录入一个或多个竞品 ASIN**（首次配置 tracker_config.json，或后续往配置里新增竞品）时，在确认配置后追加一句引导：

> 📌 这 [N] 个竞品是首次录入。建议现在跑一次 **竞品监控（competitor-monitor skill）做初次记录**，给它们建立 listing 基线——这样日后对手一改标题/价格/促销，就能立刻比出来。回复 **「初始化竞品监控」** 即可。（首次会顺带拉一截近 3 个月价格/BSR 历史背景。）

用户回「初始化竞品监控」→ 转入 competitor-monitor skill，对新录入竞品跑首次记录（存基线快照 + 拉数值历史背景）。

**边界**：同样是建议 + 用户确认，不自动跑（首次记录每个竞品消耗 2 次额度：asin_detail + keepa 历史）。已建过基线的竞品不重复提示。

## 语气

冷静、不渲染。竞品降了 $1 就说降了 $1、可能的影响是什么，不喊"警报"。数据不够下结论时说"信息不足，建议自己再看一眼"，不脑补，不奉承。

## 附：取数字段说明（模式 A）

调 asin_detail 时用 return_fields 只取追踪字段（省 token，不省次数）：
`asin,bsrRank,subcategories,nodeIdPath,nodeLabelPath,title,rating,ratings,price,sellerName,fulfillment,coupon,variations,skuList,badge`

后四个字段（coupon / variations / skuList / badge）是为**动作侦测**新增的：coupon 上撤、变体增减、AC·BS 标得失靠它们。注意它们**不增加调用次数**（还是每 ASIN 一次 asin_detail），只是多取几个字段、略增 token。

> **首次正式跑务必核对字段名**（遵循"绝不凭记忆硬编字段"原则）：`coupon`、`variations`、`skuList`、`badge`（及其子字段 amazonChoice/bestSeller）的真实命名以实测单次返回为准。competitor-monitor 实测确认过 badge.amazonChoice/bestSeller、variations、skuList、coupon 均有返回，但首次接好卖家精灵跑一个真实 ASIN 时，仍要对照返回确认字段名一致，对不上就改这里和侦测逻辑，别让侦测静默失效。

已知不可用 / 已弃用（不要再调，省额度）：
- **关键词排名（traffic_keyword）**：用单词精确查常返回空，取不到"排第几名"，维持停用。
- **父体销量（asin_prediction）**：返回的是预测估算值、非后台真实销量，且额外耗额度，不纳入每日追踪。
