00

先记住三句话，会上不容易被带着走

防关联本质不是技术问题

技术手段（独立IP、独立环境、独立服务器）只能降低「被系统误判」的概率。真正决定是否关联的，是经营主体、支付与税务资料、产品与发货信息是否重叠。同一个法人、同一张信用卡、同一批 Listing，就算每店一台服务器，也照样关联。

官方 API 与「关联」几乎无关

SP-API 是 OAuth 授权后的服务端调用，不携带浏览器指纹、不产生后台登录行为。多卖家用同一个应用不会被判定关联。所以问题 4 的答案基本可以预判：仅用官方 API，不需要为防关联给每店配服务器。真正需要环境隔离的是网页登录和 RPA。

向投资人讲的是「可控性」

不要讲"我们不会被关联"，讲"账号资产有隔离机制、凭证有加密托管、写操作可审计、数据获取有官方为主+兜底方案"。前者是无法承诺的，后者是可以出架构图和SLA的。

⚠ 表述红线（会上和汇报都要注意）
亚马逊官方政策是：同一站点原则上只允许一个卖家账号，多账号需有合法业务理由并经批准；为规避限制而开设多账号是明确违规的。所以内部口径应统一为「多主体、多站点的合规经营与数据安全隔离」，不要用"防关联""多开""绕过风控"这类表述，尤其在有投资人、有录音、有第三方在场的会议上。
01

先把三条链路分开，一半的问题自己就消失了

会上对方一旦把这三条混在一起讲，后面的答案就都不可信了。这张图建议直接投屏。

A · 官方 API 链路 风险低

怎么走：卖家在后台点授权 → 拿到 refresh_token → 服务端 HTTPS 调用
亚马逊看到：一个开发者应用、一个授权主体、一批请求
不携带：浏览器指纹、Cookie、登录 IP 语义
要防的是：凭证泄露、权限给太多、调用异常被限流

B · 网页登录 / RPA 链路 风险最高

怎么走：打开浏览器 → 登录后台 → 点击/抓页面
亚马逊看到：IP、设备指纹、Cookie、时区、操作节奏
关键：隔离不到位，这里才是关联的真正入口
要防的是：多店共 IP、共指纹、共用一份浏览器缓存

C · 公开页面抓取 风险中等

怎么走：不登录，抓竞品详情页、评论、BSR
亚马逊看到：匿名流量、爬虫特征
与店铺：不与任何店铺账号绑定，谈不上关联
要防的是：被反爬拦截、数据不稳定、数据来源合规
一句话对齐
「服务器/IP/浏览器环境」这一整套，只服务于 B 链路。如果积加的功能是纯 A 链路，那这套成本就该省下来；如果他们的功能里有 B 链路成分，那必须问清那部分走谁的 IP、谁的凭证。
02

亚马逊到底看什么：七类信号，只有三类是技术能隔离的

亚马逊未公开完整判定算法，以下是行业普遍共识的信号集合，用于内部对齐足够，不要对外当作官方口径。

信号层亚马逊侧看到的技术能隔离吗真正的隔离手段
网络层公网出口 IP、IP 归属（机房/云/住宅）、ASN、IP 地理、DNS能一店一固定出口 IP；优先静态住宅/本地宽带，机房与云 IP 段本身是被重点标注的对象，不是"更安全"
设备指纹UA、Canvas/WebGL、字体、分辨率、时区语言、硬件并发能指纹浏览器或一店一虚拟环境，环境模板不得跨店复用
本地存储Cookie、localStorage、IndexedDB、缓存能一店一份独立 profile，跨店绝不复用；这也是 RPA 最容易出事的环节
主体资料营业执照、法人、注册地址、电话、邮箱、信用卡、收款账户、税号不能只能靠业务层：不同法人主体、不同收款账户、不同税务登记。这是硬约束
经营层产品重合度、Listing 图文相似、品牌归属、发货地址、FBA 入仓、客服话术不能只能靠运营层：品类与文案差异化、发货与入仓路径分离
行为层登录时间分布、操作节奏、多账号互相访问部分任务按店铺串行化、错峰执行，避免同源批量动作
资金与合规银行账户、VAT/OSS 申报主体、EPR 注册、清关主体不能欧洲站尤其注意：VAT 号、税代、清关抬头共用是最容易被穿透的一条线
这张表最重要的用法
当对方说"我们上了独立服务器，可以防关联"时，你可以指着下面四行问：那主体资料、产品重合、VAT 主体、收款账户这几层，你们怎么处理？如果对方只能回答技术三层，说明他们做的是"环境隔离"，不是"账号安全"，这本身就是有价值的结论——不要指望ERP解决业务层问题。
03

四个流传很广但会误导决策的说法

误区 1 一个店铺一台服务器就能防关联

服务器只解决"出网 IP 不共用"。如果两个店铺用同一张信用卡、同一法人、同一批图片，服务器再多也是白买。这是最贵的无效投入。

误区 2 用云服务器（AWS/阿里云）更安全

云厂商 IP 段是公开可识别的，且大量卖家共用同一批地址池，反而更容易被标记。业界通常认为本地独立宽带 + 静态住宅 IP 的画像更接近自然人经营。这点建议直接问积加他们的 IP 是什么类型。

误区 3 API 也要每店一套独立服务器

不需要。API 的隔离靠的是每个店铺独立的 token + 加密存储 + 调用审计 + 固定出口 IP 白名单，不是物理机器。对方如果说"必须每店一台"，要么是他们有 RPA 成分，要么是架构在赚硬件钱。

误区 4 多个卖家用同一个ERP就会被判定关联

不会因为这个判定关联。但真实风险在别处：应用一旦被亚马逊停用，所有授权店铺的数据同时中断；应用授权 Role 勾太多，合规暴露面变大；供应商侧一旦泄露，是批量的。这才是会上要确认的。

05

八个问题：问法 + 追问 + 合格答案标尺 + 红旗

点开每一条。会上不需要念完全部，重点是最后那一栏——听到什么算过关，听到什么要警觉。

Q1 积加如何降低多店铺关联风险？▶
不要这么问
"你们怎么防关联？"——这种问法只会得到"我们很安全"。
改成这么问
"你们的系统里，哪些环节会接触到店铺的网页登录环境？这些环节分别用什么做隔离？纯 API 的部分占多少？"
追问
  • 如果卖家自己登录后台，是直连亚马逊，还是会经过你们的代理/服务器？
  • 历史上有没有客户反馈因为使用你们系统被关联？如果被质疑，你们能拿出什么来举证？
  • 你们内部有没有"环境隔离白皮书"或架构图可以给到我们？
合格答案
能当场把功能分成"纯API / 需登录 / 公开抓取"三类，并说明后两类的 IP 与凭证归属；能提供隔离架构图。
红旗信号
使用"绝对""不可能""百分百"这类词；说不清 RPA 部分走谁的 IP；把关联风险完全归结为技术问题。
Q2 单独服务器、独立 IP、浏览器环境，各自解决什么？▶
期望的答案
服务器 → 物理与运维隔离；独立 IP → 网络层同源；浏览器环境 → 设备指纹与本地存储。三者都不覆盖主体资料与经营层信号。对方如果能主动说出最后这半句，说明是真的懂。
必须追问
  • IP 是什么类型：机房 / 云 / 静态住宅 / 本地宽带？一个 IP 绑几个店铺？是否是共享池？多久换一次？
  • 换 IP 的时候，原有环境是否跟着迁移？迁移过程中两店会不会短暂共用一个 IP？
  • 浏览器环境是租户级还是一店一份？环境模板是否复用？
合格答案
能明确说出 IP 类型与"一 IP 一店"的绑定规则；承认技术层有边界，业务层需我们自己处理。
红旗信号
"共享 IP 池但很安全"；"我们是云服务器所以更稳定"；无法回答一个 IP 绑几店。
Q3 哪些功能走官方 SP-API，哪些必须 RPA？▶
要的东西
不是口头分类，是一张表：功能 → 走的接口名 → 需要的授权 Role → 调用频率 → 是否含写操作。这张表我们要拿回去做架构依据，请他们会议后发正式版。
追问
  • 评论、商机探测器、账户健康、自然搜索排名、后台通知 —— 这五项分别怎么做？
  • 广告数据是走 Selling Partner API 还是独立的 Advertising API？授权是不是要单独做一遍？
  • 写操作（改价、改库存、改 Listing、提交货件）哪些支持 API，哪些只能 RPA？写操作有没有二次确认？
合格答案
能区分读/写；能明确广告是独立授权体系；能提供接口清单文档。
红旗信号
"全部支持 API"——这不可能，评论和商机探测器没有接口；或者把广告 API 说成 SP-API 的一部分。
Q4 只用官方 API，还需要每店部署独立服务器吗？▶
我们的判断
不需要。API 调用是服务端 HTTPS 请求，隔离靠凭证与权限，不靠机器。但建议要求固定出口 IP 白名单，理由是便于审计和限流管理。
追问
  • 你们的 API 调用是从共享集群出网，还是按租户隔离出网？共享出口会不会导致限流互相影响（一个店铺把额度用光，其他店被拖慢）？
  • 如果我们要私有化或专属实例部署，有没有这个选项？成本量级？
合格答案
承认不需要物理隔离；能说明限流是按 token 还是按应用维度控制（这个差别很关键，按应用维度会让多店互相拖累）。
红旗信号
坚持"必须每店一台服务器才能安全"，且说不出技术理由。
Q5 凭证、Cookie、数据、任务怎么隔离？▶
这是最技术的一问
问到底层实现，别让他们用"加密存储"一句带过。要问"用什么加密、密钥谁管、谁能解出来"。
逐项问
  • Token：refresh_token 存在哪？用什么加密（是否 KMS/信封加密）？密钥由谁持有？我们能不能导出？
  • Cookie：RPA 的会话是存本地还是云端？是否明文入库？保留多久？
  • 数据：多租户是同库同表加字段隔离，还是独立库/独立 schema？谁有跨租户查询权限？
  • 任务：同一店铺的任务是否串行排队？多店是否可以并发？失败重试会不会形成突发批量请求？
  • 人：你们内部工程师能不能看到我们的明文凭证？有没有审批与操作留痕？离职如何回收？
合格答案
能说出具体加密方案与密钥归属；有审计日志；支持一键撤销授权；我们能自己导出全量数据。
红旗信号
"这些属于内部实现不便透露"；"由我们统一保管，绝对安全"；数据导出要额外收费或需要人工。
Q6 多个卖家授权同一个应用，风险在哪？▶
先把逻辑说清
亚马逊不会因为"大家用同一个ERP"判定账号关联。真实风险是三类：①单点故障——应用被亚马逊停用或审计不通过，所有授权店铺数据同时断；②合规连带——供应商违反数据保护要求被处罚，我们作为数据控制方会被牵连；③授权过宽——Role 全勾，等于把买家信息、税务信息的访问权交出去。
追问
  • 你们通过亚马逊的数据保护安全评估了吗？有没有 SOC2 / ISO27001？最近一次渗透测试是什么时候？
  • 应用被亚马逊限流或停用的历史？恢复需要多久？有没有 SLA？
  • 能不能支持我们用自己注册的开发者应用授权（私有应用模式），token 落在我们自己账号下？这能把单点风险降到最低，强烈建议问。
  • 授权时最少需要勾哪些 Role？能不能只给只读？
合格答案
有第三方审计报告或能提供安全白皮书；支持最小权限授权；支持私有应用或专属部署；对中断有明确 SLA 与数据迁移承诺。
红旗信号
"不需要审计"；要求勾选全部 Role 才给用某些功能；没有书面 SLA；拒绝谈退出时的数据迁移。
Q7 官方 API 拿不到、必须靠 RPA 的数据有哪些？▶
要的东西
一份兜底清单，至少包含：数据项 / 抓取方式（登录后台 or 公开页）/ 抓取频率 / 稳定性 / 断供时的替代方案。
必须问清责任
  • RPA 登录后台用的是谁的账号？主账号还是子账号？密码和验证码谁保管？
  • 如果因为 RPA 触发风控导致账号被限制，责任怎么划分？合同里有没有写？
  • RPA 断供（页面改版、验证码升级）时，多久能恢复？有没有第三方数据源兜底？
合格答案
用子账号 + 限定权限 + 可随时回收；承认 RPA 有断供风险并给出兜底方案；合同里有责任条款。
红旗信号
要求提供主账号密码；说"我们从不触发风控"；不书面约定责任。
Q8 我们现有架构还要补哪些安全和隔离措施？▶
先给结论
把下面第 06 节的清单直接给他们看，请他们逐条评估"你们能不能帮我们做到 / 需要我们自己做"。这样会议就从"听他们介绍"变成"对着清单验收"。
尤其要提的一条
数据出境与 GDPR。我们做欧洲站，买家信息属于个人数据。如果数据存放在境内服务器，跨境传输需要合法机制（标准合同条款等）与数据处理协议。这条很少有人在技术会上提，但它是尽调一定会问的。请确认：数据存哪个区域？有没有 DPA？子处理商名单能不能给？
06

现有架构补强清单（按优先级，可直接当验收标准）

P0 不做就有实际风险
每个店铺独立 token，加密存储，密钥与应用分离，可一键撤销
授权按最小权限勾选 Role，只读优先，写权限单独审批
网页登录/RPA 环境一店一份，绝不复用 Cookie 与指纹模板
禁止使用店铺主账号做自动化，一律子账号 + 限定权限
签数据处理协议（DPA），明确子处理商与数据存放区域
写操作（改价/改库存/改Listing）留审计日志，可追溯操作人与时间
P1 上规模前必须补齐
出口 IP 固定并加白名单，便于异常排查与限流定位
多租户数据隔离（独立库/schema），跨租户查询需审批留痕
任务按店铺串行 + 错峰，避免同源批量动作
监控告警：授权失效、限流触发、调用异常、RPA 断供
数据全量可导出，退出合作时 token 与数据按期删除并出凭证
员工权限分级与离职回收流程
P2 有余力再做，但投资尽调会加分
私有开发者应用（BYO App），把授权主体收回到自己名下
关键数据双来源交叉校验（官方 API + 第三方），防单点断供
账号健康与政策通知的自动巡检（官方无接口，需兜底）
主体资料台账：法人、收款、VAT、EPR、清关抬头的唯一性校验
会议结束前 必须带走的三样东西

三句话版本
① 账号资产是我们最大的单点风险，我们做了双轨隔离：技术层（IP、环境、凭证）与主体层（法人、收款、税务），两条轨道都在推进。
② 数据获取以官方接口为主、兜底手段为辅，日常运营数据绝大部分走合规路径，只有亚马逊不对外开放的评论与竞品情报用补充方式，且明确知道断供影响范围。
③ 凭证加密托管、写操作可审计、数据可导出，这套底子决定了我们能不能安全地从几个店扩到几十个店。
风险项具体表现缓释措施（可被追问的话术）
账号关联多店铺被判定为同一经营者，合并或封停技术层一店一环境一 IP；主体层不同法人、不同收款、不同税务登记；经营层品类与文案差异化。承认技术不能替代业务隔离
数据中断供应商应用被停用，全部店铺数据同时断要求支持私有应用模式把授权收回自己名下；关键数据双来源；有全量导出与迁移预案
合规处罚买家个人数据跨境、授权过宽、留存超期最小权限授权、签 DPA、明确数据区域与留存期限、按亚马逊要求定期安全评估
