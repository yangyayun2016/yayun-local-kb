一、先看结论：门几乎全开着

85 个接口，75 个通。被拒的 10 个，做 SC / FBA 的一个都用不上

先把被拒的说清楚，免得惦记。被拒的不是能力不足，而是这些接口本来就属于别的身份、别的项目。

被拒的接口为什么被拒谁才需要
买家姓名 / 地址 / 邮箱需额外申请受限角色，涉及个人信息，要过一轮数据安全审核需要买家信息的场景
自发货买面单 / 承运商账户同样需受限角色与数据安全审核自发货（FBM）卖家
发票 API供应商账号专用VC 账号
Seller Wallet / 收款方式需「账户信息服务商」身份银行与金融机构
外部履约（三个接口）需单独入驻的项目，未入驻一律 403自有仓承接亚马逊订单
供应链追踪（外部渠道货件）同上，属于需单独入驻的项目未入驻账号无入口
敏感信息实测：该藏的藏得很干净 调买家信息接口，返回只有一个订单号；调收货地址，只给到城市、州、国家，再往细就需要敏感信息权限的开发者了。 换句话说：能给你的一分没少给，不该给的一分没多给。

编者注：被拒清单里的「供应链追踪（外部渠道货件）」指需单独入驻的供应链项目；与下文第六节 8 月新增的货件追踪接口不是同一个入口，具体以实测能力表为准。

三、SP-API：今年新出的七块，挑运营用得上的讲

老接口能干什么，文档写了很多年，这里不重复

3.1 新版订单接口1 月

旧版要拉齐一单信息得调十个操作：订单、订单行、买家信息、地址、税、支付……新版只剩两个：搜订单、查一单。

一单的信息用 includedData 点名要，把全部取值试过一遍，都通：收入拆分、费用、促销、取消、配送、包裹、税、支付、Easy Ship 订单号。

收入拆分最有用 一单的总收入下面挂着分项，每一项带类型和小计。周会上运营说「这个 SKU 上周 200 单」，老板问「200 单收进来多少？扣完促销呢？」——以前要等财务月底出表，现在订单接口里就有。

7 月又加了两个字段：取消是怎么执行的，以及面单打印窗口。

两条要记住的变化 旧版订单接口 1 月已宣布淘汰，FBA 订单里的买家邮箱也去掉了。新做的工具，别再接旧版。

3.2 促销 API两周前刚上线

以前促销这块 API 完全没有入口，跑了多少秒杀、优惠券花了多少预算，只能去后台一个个点。新上线的促销接口三个操作：

searchPromotions
按条件搜

返回每个促销的标题、预算、起止日期、状态、优惠力度、促销 ID、商城，共 26 个字段，还带费用快照：前置费用多少、按销售额抽多少、封顶多少。秒杀、优惠券、价格折扣、凑单促销都在一张表里。

getPromotion
按 ID 取详情

拿某一个促销的完整数据。

getProductSelection
取商品选择

支持分页、超过 100 件商品，每件商品带专属优惠。

这三个操作里最值钱的一行字：验证问题。促销级的验证问题、商品级的验证问题，接口直接返回。

周四下午运营建了一场秒杀，30 个 ASIN，后台显示「部分商品不符合条件」。哪几个？为什么？后台不说，只能一个个猜，甚至开 case 让客服查。半天过去找到 4 个：两个价格不满足，一个库存不够，一个上周刚做过折扣。
以前这半天是自己排查，现在这四个原因接口里一次返回。

同一批更新里，优惠券和促销的表现报表加了一个字段，跟促销 API 的 ID 能对上——促销的花费和促销的效果，头一回能在 API 里对到一起。

它只有查，没有建 秒杀优惠券还得后台手建。但你已经能算清每一场花了多少、换来多少、以及为什么没通过。创建功能年底上，且创建时就能直接验证会不会报错、实际原因是什么。

3.3 财务三件新东西7 月

结算周期汇总

一行一个结算周期，净收入下面挂拆分。

账户余额

按类型分：可用、预留、递延、账户级预留。

预计放款

同一天加的独立接口。下一笔什么时候到、多少钱、打到哪张卡的尾号。

老板问：这个月的款什么时候到？
以前的答案是「大概月中」。
现在有一个字段叫 scheduledDate。

顺带一句：交易流水 1 月起能按订单号筛了。一个订单号进去，这单的每一笔收入和扣费出来。

3.4 多渠道配送新版 MCF7 月

订单列表可以直接带货件信息，一次拉回 34 个字段：状态、配送配置、收件地址、行项目、货件。做独立站或其他平台用 FBA 发货的，接这个。老版本还能用，但新做的接新的。

3.5 相似商品与竞品价格5 月正式推出

给定一个 ASIN，返回它的相似商品，不限自家，任意 ASIN。现场当场验证：把幻灯片上那个阻力带的 ASIN 丢进去，返回 6 个相似商品；再把这 6 个分别丢进去，每个又返回 6 到 7 个。三层下去，一个品类的竞品图谱就出来了。

同一个接口，includedData 里再点三样，竞品的价格一起回来：

includedData返回什么做监控时怎么用
featuredBuyingOptionsBuy Box 现价、是谁的、按会员身份分段盯 Buy Box 归属与价格变动
referencePrices划线价 WasPrice、亚马逊的竞争价 CompetitivePrice判断对方是否有价格优势空间
lowestPricedOffers该 ASIN 下各卖家的最低报价、运费、是否 FBA看同链接的卖家结构与配送方式

批量打了 14 个竞品 ASIN，全部 200。一次最多 20 个，限流每 30 秒一次——做成监控竞对的工具正合适。

促销价那一层，如实说明 7 月发布记录说每个报价下面加了 promotions：促销类型、减多少或打几折、折后价。字段在官方数据模型里已确认，就挂在每个卖家报价下面。但这次抽的 14 个 ASIN 当时都没在跑促销，没有亲眼看到它填上值——先如实说，后续实测再补。
为什么这条重要 以前盯竞品价格靠第三方插件，按月付费，数据是它抓的，抓没抓到、准不准，你没法验。现在同一份数据从亚马逊自己的接口出来：信息是真的，还免费。 另外 Listing 接口 7 月起支持一次查同区域多个站点，美国和加拿大一次带回，多站点改价前先看一眼。

3.6 供应链追踪与通知过滤8 月 / 5 月

8 月 5 号出了追踪接口：按承运商单号、集装箱号、提单号查外部渠道货件的里程碑和预计送达，配一个新的通知类型。

通知这边 5 月加了过滤表达式。以前订阅一个订单变化通知，所有订单的所有变化都推给你；现在可以写一条表达式，只推你要的那一类。通知要自备 AWS 队列，这条没变。

3.7 Data Kiosk：不是取数据，是取分析结果重点

三种取数方式的区别，一句话讲清：

普通接口
取记录

订单、库存、Listing。一次一批对象，字段固定。

报表接口
取表

报表类型固定，119 个字段全给你，自己再筛。

Data Kiosk
取分析结果

你写一段查询，点名要哪些维度、哪些指标、什么粒度，亚马逊在后台聚合好，给你一份结果文档。

现场建了一条：近 7 天按日的销售额、件数、退款率、Sessions、页面浏览、Buy Box 占比、转化率。只点了 19 个字段，回来就是 19 个字段，一行一天。字段你点名，粒度你定，亚马逊替你算好。

数据集包含什么粒度与范围
销量流量 Sessions、页面浏览、Buy Box 占比、转化率、退款率 按日 / 周 / 月；按父 ASIN / 子 ASIN / SKU；可回溯两年。今年 1 月和 2 月加了 B2B 的退款、反馈、索赔指标
经济学 每个 ASIN 的销售额、佣金、FBA 费、仓储费、广告费、净收益，还带费用变更的预估 等于官方版的「单品利润」。普通接口没有现成的，只能拉财务流水自己拼
周会要看每个 SKU 上个月赚了多少。
以前：拉订单、拉财务流水、拉广告花费、拉仓储费，Excel 里对 ASIN 拼四张表。
现在：一条查询，指定月粒度、子 ASIN，字段点净收益和各项费用。等几分钟，文档下来。
它不适合什么，也说清楚 ① 不是实时的，数据隔天，出结果几分钟到几十分钟；② 没有调度，定时跑要自己的工人去建查询；③ 同一条查询同时只能跑一个；④ 只有分析数据集，没有订单明细、货件这类业务对象；⑤ 要品牌分析角色，店铺得有品牌备案。

卖家后台有个 Schema Explorer，写查询前先去看每个数据集有哪些字段。

还有几条，一句话带过

报表与 Feed

四、Ads API：另一套体系，也只说今年的

另一个授权、另一份文档。广告工作台从 7 月底起每天拉报表，8 月中接了 AMC

这次又拿真账号把 48 个接口只读打了一遍。老接口不讲，只讲今年新出的。

4.1 新的账号模型6 月 18 日 GA

广告主账号管理接口 GA，一个账号在各国的映射一次带回。旧的账号接口 2027 年 7 月关停，新做的必须接新的。实测：通过。

4.2 品类基准5 月 18 日全球 GA

你的品牌和整个品类比，曝光、点击率、ACOS、ROAS 各给三档：前 25%、中位、后 25%。

运营说：我们 ACOS 28%，算不错吧。
拉一下基准：这个类目中位 22%，前 25% 是 15%。
「不错」这两个字，以后有官方参照了。
这一条对数据分析的意义 以前判断广告表现好不好，靠「跟自己上个月比」。有了品类基准，可以跟类目比——同一个 ACOS，在低竞争类目算优秀，在高竞争类目可能只是及格。给建议、定目标、做复盘，都有了外部锚点。

4.3 官方 MCP Server2 月开放测试 · 7 月起支持 OAuth 2.1

账号、AMC、账单、活动管理、报表、流订阅，全部做成了 AI 能直接调的工具，还带十几个官方 skill。用现有的 LWA 客户端就能接，不用另外申请。

这意味着：你让 AI 管广告账号，官方已经把接口层铺好了。

五、从授权到出表：能力这一头，没有门槛

拿能力不难，难的在另一头
STEP 1

应用 ID + 一个随机串 + 回调地址。文档是公开的，整个过程不调任何接口。
STEP 2
群里点开
在店铺登录着后台的那台环境上，同事点开链接，看到授权页，列着这个应用要哪些权限。

STEP 4
令牌落库
亚马逊跳回回调地址，token 已经落在服务器上。前后不到一分钟，没有人写一行代码。
摸一遍接口要多久 85 个接口，从写探测脚本到出表，AI 跑了十来分钟；后来对照官方发布记录补今年的新版本，又二十几个，五六分钟。 中间有十几个接口报 400，全是传参没传对——日期格式、枚举值写错、必填漏了。改一轮再跑，又通了一批。

六、真正的门槛：限流

能力不难拿，难在限额——这决定了架构长什么样
接口实测限流对架构的含义
报表创建约 1 分钟 1 次连建 6 份，第 1 份和第 3 份直接 429。报表要排队，不能并发乱建
新版订单搜索约 3 分钟 1 次最狠的一条，决定了订单同步只能低频批处理
相似商品 / 竞品价格30 秒 1 次（单次最多 20 个 ASIN）适合做批量竞对监控，不适合实时查价
财务流水每秒 0.5 次对账类任务要拉长节奏
库存每秒 2 次可支撑较高频的库存巡检
入库货件每秒 5 次货件类工具可以做得比较顺手

限流相对快慢（数值越大越慢）

两次调用之间的最小间隔（秒）

从限流倒推出的四条架构原则

① 不能前端直调

限流这么紧，前端点一下查一次必然 429。API 只能由服务端在后台消费。

② 不能人盯

报表创建一分钟一次、订单搜索三分钟一次，人盯着只会浪费时间。它天生就该是自动化任务。

③ 夜里跑，早上看

夜里在服务器上慢慢跑，跑完落到自己的库里；早上人打开网页看结果。

④ 有时间窗的数据必须自己存

搜索词那种亚马逊只保留 65 天的数据，必须每天拉、自己存，过期就永久没了。

配套的设计原则：一次调用把活干足 库存汇总一次给整个站点，报表一次给一个月。你要的是「把一批 ASIN 一次带上」，别一次调一个数据点。 在限流面前，「少次多量」永远优于「多次少量」。

七、难的是：明天谁看

数据全在库里，和数据被人用，是两件事

有一种做法很诱人：全拉一遍，建一个自己的「数据中台」，所有数据都在库里，想看什么看什么。这件事最好不要做。

我见过有人花三个月把订单、库存、财务、广告全拉进一个库，看板做了二十几张，上线那天发了一个群公告。
一个月后问运营：最近打开过几次？
答：开会前看一眼利润那张。其他二十几张，谁也说不出是给谁看的。

7.1 挑数据只问四个问题

② 在哪个会上看？

没有会议场景的数据，基本不会有稳定读者。

① 这个数据明天谁看？

说不出具体的人，就先放着。表里躺着不费钱。

③ 它替掉了哪一步手工？

替代不了的，是加税不是减负。

④ 能节省多少时间？

省不出可量化的时间，优先级就往后排。

四个都答得上来，就接；一个答不上来，先放着。

7.2 这一刀怎么切：自动创建和核对 FBA 货件

为什么第一刀是它？因为运营每票货有一起发的产品，分仓后要手动核对一遍箱号，然后手抄、对一遍追踪编号、下一遍箱标，最后给到仓库。箱数多的一票三四十分钟，一周十几票。这个时间成本看得见、量得出。

环节原来怎么做方案怎么做
发现后台创建「Send to Amazon」，把每箱 SKU 和数量抄进公司 Excel 模板，追踪编号一票一票复制，箱标一票一票下载。三个动作，一票二十分钟不做「货件管理系统」，只做两件事：① 识别仓库给的可发数据，据此创建货件；② 创建后把工作流程编号记下来
方案—拉回这票的计划、货件、箱单、箱标，按公司模板生成 Excel，箱标 PDF 打成一个包
跑通—第一票真货件 5 票 51 箱：创建 2 分钟，输出货件信息 41 秒，Excel 与 8 月那份人工样本逐格一致
给团队用—第二天运营验收，顺手踩出一个坑：走亚马逊合作承运人的计划，列表接口不列，凭编号直查、或者创建的时候记录才有。这种事文档里没写，只有真跑才知道
好处—运营一周省回一两个小时；更重要的是箱单不会抄错了。从发现到每天在用，两天
方案里的每一个取舍，都从运营的桌面上来 运营手上先有仓库给的可发数据 → 所以入口就是这份数据，不让他重新录一遍。
他后台建完货件，手边就是那个工作流程编号 → 所以第二步只要他粘一个编号。
他最后要交给仓库的是一份公司模板 Excel 和一包箱标 → 所以输出就是这两样，不多不少。
方案架构做的，就是把工具长在用户已经在做的动作上。

7.3 方法论：解决方案架构师（SA）

有一个岗位干的事很具体：对着一个问题，设计解决它的方案。大会上亚马逊官方的人自我介绍，报的就是这个头衔。

定位：站在业务视角，用产品能力、API、系统集成，设计落地方案解决业务问题。重点在方案设计、选型、接口对接规划、风险评估，而不在写多少代码。
SA 的五件事对应货件那一刀
① 梳理业务痛点，把业务需求翻译成技术方案痛点是手抄箱单
② 基于平台提供的 API / SDK / 接口能力，设计系统对接流程接口是入库货件那一族
③ 画架构图、接口时序、数据流转，定义字段、鉴权、异常处理流程是识别可发数据建货件、再粘编号出文件包
④ 评估 API 限流、安全、性能、成本，给出集成方案限流是每秒五次
⑤ 对接开发、测试、业务方，推进方案落地，排查集成问题落地是第二天运营验收
为什么单拎出来说：往后，人人都是开发者 代码这道门槛，AI 已经拆了。你能把业务说清楚，你就能做出工具。门槛没了，差别在哪？谁做的工具好用、真有用，看的是设计思路。 工具也是产品，运营就是它的用户——跟做一款产品好不好卖，是同一个道理。

八、避坑与取舍清单

把这一页贴在工位上
接之前

① 先确认自己是什么身份——FBM、VC、银行类身份需要的接口，你做 SC/FBA 的根本碰不到，别浪费时间。
② 新工具不要接旧版订单接口（1 月已宣布淘汰）。
③ 想清楚限流能不能支撑你的交互设想。
④ 只读探测先打一遍，只记状态和字段名，别留店铺数据。

做的时候

① 400 报错先查传参：日期格式、枚举值、必填项，十有八九是这里。
② 一次调用把活干足，别一次调一个数据点。
③ 有时间窗的数据（如 65 天搜索词）必须每天落库自存。
④ 定时调度、重试、幂等，都得自己写——平台不提供。

上线之后

① 别做二十几张看板。先做一张真有人每天开的。
② 走合作承运人的货件计划，列表接口不列，记得凭编号直查或创建时记录。
③ 用品类基准校准「不错」这两个字的含义。
④ 报表与促销 ID 已能对上，促销花费和效果要在同一张表里看。

心态上

① 能力是亚马逊给的，方案是你自己的。前者一天摸完，后者决定它是工具还是摆设。
② 第一刀不是周报——周报已经有 ERP 顶着，多一个来源就是给运营加税。
③ 验收标准只有一个：这个工具明天替谁省掉哪一小时。答不上来，不做。
