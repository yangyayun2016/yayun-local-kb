二、AI、MCP 与 SP-API 年度更新

2.1 核心概念

SP-API（Selling Partner API，销售伙伴接口）：软件向亚马逊读取或提交业务信息的接口集合，可以把它理解成 ERP 与亚马逊之间的“业务连接口”。它不等于 Sponsored Products 商品推广广告；广告数据和操作在本次分析演讲中另列为 Ads API。

MCP（Model Context Protocol，模型上下文协议）：让 AI 客户端连接外部工具的一种约定。白话理解：AI 负责理解需求，连接的工具负责查询文档、处理工作流或调用获授权的功能。具体能做什么取决于服务器实际提供的工具和权限。

2.2 现场展示了什么

IMG_2404 的 Kiro 界面标题为 DataKiosk MCP Demo，左侧显示连接项：

  • builder-mcp，界面显示 36 tools。
  • sp-api-dev-assistant。
  • sp-api-workflow，工具数量后半被截断，不据此确认总数。

界面还显示 Specs、Agent Hooks、Agent Steering & Skills，以及 Vibe、Spec 两种工作入口。能确认的是演示环境已连接这些服务器；不能由此确认所有公众账号都能直接使用相同配置。

2.4 对资料整理的启发

可把会议资料沉淀为三个层次：原始证据、业务解释、实际验证。今后向 AI 提需求时，可以写成“查询某站点某段完整日期的某类数据，说明字段口径，再输出异常与证据”，比只说“帮我优化店铺”更容易得到可检查的结果。

四、Amazon Business：企业购与 B2B 专属工具

4.1 从个人消费者运营走向企业采购运营

B2C 是卖给个人消费者，B2B 是卖给企业或机构；Amazon Business（AB） 指亚马逊企业购。

IMG_2322 的观点是：B2C 工具链已覆盖选品、流量、价格、配送、售后等环节，卖家需要面向企业买家的专属工具。投影片提出的困难是：2C 和 2B 放在一起运营，难以针对企业买家提升选品、流量与曝光。

现场列出的环节 代表工具或能力
选品与便利 商机探测器、选品指南针、品牌分析、A+ 与高级 A+
流量与转化 买家评论计划、优惠券组合拳、旺季活动、展示型推广、商品推广、品牌推广
多件订单 买一送一、订阅并保存
价格竞争力 自动定价、价格折扣、多买多省
物流配送 供应链智能托管、全球物流、跨境承运伙伴方案、入仓分销网络、多渠道分拨、亚马逊物流、卖家自配送、新品入仓优惠计划
售后复盘 退货管理、冗余库存管理

4.3 打印 PO 编号与公司名称

PO（Purchase Order，采购订单）编号：企业内部用于匹配采购、收货和付款的编号。例：收货仓库看到包裹上的 PO，就能更快对应到公司的采购单。

现场列出的痛点：企业客户要及时核对包裹与订单；缺失信息会打乱三方匹配流程；共用收货口难以盲分拣；人工核对拖慢付款；退货与缺陷风险增加。这些是投影片列出的业务问题，不是对你店铺的诊断。

步骤 照片给出的实现方向
1. 识别 AB 订单 检查 Orders API 响应 programs 是否包含 AMAZON_BUSINESS
2. 获取 PO 编号 Orders API v2026，includedData = BUYER，读取 buyer.buyerPurchaseOrderNumber
3. 获取公司名称 读取 recipient.deliveryAddress.companyName
4. 打印到标签 映射到承运人参考字段，例如 FedEx P_O_NUMBER、UPS Reference

来源：IMG_2327.jpg。脚注称通过“购买配送”购买的货件标签会自动打印 PO 编号和公司名称；具体覆盖条件需后续核实。

建议验证方式：用一个获授权的企业购测试订单，逐项对照订单字段、ERP 展示和最终标签；检查长公司名称是否截断、PO 缺失时是否明确提示。该建议是会后实践设计，不是现场已完成的操作。

五、全新 Orders API：把订单信息集中获取

5.1 新 GET 工作流

IMG_2331 的标题为“全新 GET 工作流”，强调“流程统一，一次调用获取全部信息”。页面展示：

  • 操作名称：SearchOrders。
  • 路径：/orders/2026-01-01/orders。
  • 筛选维度：创建时间前后、最近更新时间前后、订单状态、商城 ID、履约渠道（FBM/FBA）、包含的数据集。

白话解读：以前可能需要分开查询订单、买家、地址、包裹，再在软件里拼接；现场展示的方向是让开发者按需获取更完整的订单对象。这里的“一次调用”是演示表达，不能理解成任意数量的订单都不用分页或补充查询。

5.2 代码演示中的变化

IMG_2333 显示 Python 演示注释 “Orders API 2026-01-01”“1 call per order | no RDT”。代码用 included_data 请求 BUYER、RECIPIENT、PROCEEDS、PACKAGES。

演示所列变化 对开发工作的含义
fulfillment_channels → fulfilled_by，MFN → MERCHANT 请求字段与枚举需重新映射
order_statuses → fulfillment_statuses，Unshipped → UNSHIPPED 状态拼写及大小写不可直接沿用
去掉 payload 外层 旧响应解析代码可能需要调整
amazon_order_id → order_id 订单标识字段的读取方式需核对
included_data 按需获取多类信息 数据选择与应用权限需要一起检查
PII 由应用角色限制，不再往返获取 RDT “不需要 RDT”不表示任何应用都能获取敏感信息

PII 是可识别个人的信息，如姓名、地址；RDT 是 Restricted Data Token，受限数据令牌。上表字段为现场 Python 示例写法，不等同于所有语言 SDK 或 HTTP 参数的最终命名。

同组照片也有表达差异 IMG_2331 示例使用 status=Unshipped，IMG_2333 的代码则是 fulfillment_statuses=["UNSHIPPED"]。一个是幻灯片 URL 示例，一个是 Python 演示；不要拼接成一段未经验证的可运行请求。最终参数应按实际采用版本的接口定义核对。

5.3 对运营的实际影响

可以向 ERP 团队提出的需求包括：订单同步能否同时带出企业购标识、PO、收货公司、金额与包裹；同步失败是否有提示；更新后的订单能否重复抓取而不重复建单。

验收时更应该看“有没有漏单、重复单、缺地址或丢包裹”，而不只是看接口是否返回成功。

六、Listings API：同一区域多商城检索

Listing 是卖家在某个站点的商品刊登信息；Marketplace（商城／站点） 是具体销售市场。ASIN 是亚马逊商品标识，SKU 是卖家用于管理库存和刊登的编码。

6.1 照片可确认的新增能力与边界

IMG_2349 介绍 getListingsItem 与 searchListingsItems：

  1. 可接受同一区域的多个商城 ID，一个请求检索多个商城的商品信息。
  2. 响应可包括概要、报价、属性与问题；各项带商城 ID，便于识别来源。
  3. 可以减少对同一商品逐站点连续调用。
  4. 对单商城请求保持向后兼容。
  5. 仅适用于卖家；投影片说明供应商代码映射至单一商城。
  6. searchListingsItems 的筛选与排序（如 withStatus、sortBy）按第一个 ID，即主商城进行评估。

容易踩的坑：返回多个站点的数据，不等于每个站点都独立执行了一次相同筛选；第一个商城 ID 的选择会影响查询结果。也不能把“同一区域”扩展为任意跨区域组合。

6.2 运营场景与待补内容

适合建立同一 SKU 在多个站点的属性、报价与问题清单。整理者建议报表至少保留“卖家／账号、站点、SKU、ASIN、问题类型、抓取时间”，避免不同站点覆盖彼此。

议程中的主题是“首次提交即成功上架 ASIN”，但本批没有完整的商品类型要求、提交前校验、问题修复与发布结果页，因此暂不重建一套声称来自现场的完整上架 SOP。

七、FBM 与 Easy Ship：把自配送流程串起来

FBM（Fulfilled by Merchant，卖家自配送）：由卖家安排履约。FBA（Fulfillment by Amazon，亚马逊物流）：由亚马逊的相关仓储配送体系履约。Easy Ship 是现场讨论的配送服务，具体开通站点、仓库与资格未从这些照片确认。

八、促销与定价 API：活动、竞品与推荐报价

8.1 Promotions API 的能力地图

IMG_2412 的统一输出写了：

  • 自然销量 = 总销量 − 广告销量。
  • TACoS = 广告支出 ÷ 总销售额。
  • 从展示到点击、从会话到购买，贯穿付费与自然渠道。

会议中的简化公式，需要口径校验后才能用于真实店铺 orders7d 是订单指标，不能直接当作销量件数；sales7d 是广告归因销售额，不能直接与任意净销售额相减。订单日期与广告归因日期、退款处理、币种、站点、归因窗口及跨商品归因都可能不同。未对齐前，“总量减广告量”最多保留为待验证差额，不能命名为准确的自然销量，也不能据此证明广告带来的增量。

整理者提出的可执行拼表顺序：

  1. 先固定账号、商城、币种、站点时区、完整日期与数据更新时间。
  2. 商品级表按账号＋商城＋日期＋子 ASIN 汇总；若用 SKU，先确认 SKU 与 ASIN 映射是否一对一。
  3. 广告活动／广告组先聚合到同一商品日期粒度，再关联整体销售；否则多个活动会把同一商品的总销售额重复计算。
  4. 保留稳定的活动和广告组 ID，名称主要用于展示；这一点是实现建议，照片只列出名称字段。
  5. 同时保存广告归因窗口和字段定义，区分订单数、销量件数、订购销售额、净销售额与广告归因销售额。
  6. 检查缺失、重复、分母为零与广告归因回补，再计算比率；不能把空值一律当零。

11.6 转成运营能回答的五个问题

卖得怎么样？ 订单、销售额、平均售价、会话与浏览 完整日期，对比前一天／上周同日，退款口径

12.2 最需要保留的四个判断

  1. 读取能力与写入能力分开看。促销读取已发布的现场口径，不等于创建更新也已经开放。
  2. AI 输出要回到版本与测试。迁移演示有明确的预发布提示，与另一页版本不同，不能直接上线照用。
  3. 数据连接要先统一口径。站点、时间、币种、粒度和归因窗口对不上，漂亮的统一看板也可能误导运营。
  4. API 接入包含持续维护。同步、分页、错误处理、权限、删除与测试，都是软件可用性的一部分。
