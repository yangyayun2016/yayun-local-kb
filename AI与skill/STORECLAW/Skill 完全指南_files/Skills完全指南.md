# Skills 完全指南：规范、撰写、评测与迭代

版本：2026-05-16

适用对象：所有需要编写、审核、发布、维护和优化 Agent Skill / 自定义技能 / 平台技能包的人。

本指南基于两类材料合并而成：

- 技能包与 `SKILL.md` 的具体格式规范：`SKILL.md` 必需，`scripts/`、`references/`、`assets/` 可选。
- Skills 五原则 TRACE：Trust、Reliability、Adaptability、Convention、Effectiveness。

一句话标准：

> 一个高质量 Skill = 明确触发 + 清晰流程 + 可靠资源 + 安全边界 + 可验证结果。

## 1. Skill 的本质

Skill 不是一段普通提示词，也不是一份冗长说明书。

一个 Skill 应该是给 Agent 使用的“可复用能力包”，它把某类任务所需的专业知识、执行流程、工具脚本、参考资料和输出标准组织起来，让 Agent 在遇到对应任务时可以稳定、高质量地完成工作。

一个好的 Skill 通常提供四类价值：

1. 专门工作流：把某类任务拆成稳定步骤。
2. 工具集成方法：告诉 Agent 怎样使用特定文件格式、API、平台或脚本。
3. 领域知识：沉淀业务规则、数据口径、公司规范、行业经验。
4. 可复用资源：提供脚本、模板、参考资料、素材等，减少重复劳动。

Skill 应该回答五个核心问题：

| 问题 | Skill 中对应内容 |
| --- | --- |
| 什么时候用？ | `description` 中的能力和触发场景 |
| 解决什么问题？ | `Purpose` |
| 怎么执行？ | `Instructions` |
| 能用哪些资源？ | `scripts/`、`references/`、`assets/` |
| 什么不能做？ | `Guardrails` |

## 2. 技能包目录规范

推荐技能包结构如下：

```text
skill-name.zip
└── skill-name/
    ├── SKILL.md
    ├── scripts/
    │   └── example.py
    ├── references/
    │   └── knowledge.md
    └── assets/
        └── template.png
```

### 2.1 必需文件

`SKILL.md` 是必需文件，是 Skill 的入口说明文件。

它必须包含：

- YAML frontmatter。
- `name` 字段。
- `description` 字段。
- 正文说明。

### 2.2 可选目录

`scripts/` 用于放可执行脚本。

适合放入脚本的场景：

- 同一段代码会被重复生成。
- 操作容易出错，需要确定性。
- 流程依赖参数校验、格式转换、批处理、渲染、解析等。

`references/` 用于放参考资料。

适合放入参考资料的内容：

- 产品文档。
- API 说明。
- 数据库 schema。
- 业务规则。
- 品牌规范。
- 行业知识。
- 长案例或复杂范式。

`assets/` 用于放最终输出会用到的素材。

适合放入素材的内容：

- 模板。
- 图标。
- 字体。
- 图片。
- 示例文件。
- 前端或文档工程骨架。

### 2.3 命名规范

推荐统一使用：

- 小写英文字母。
- 数字。
- 连字符 `-`。

示例：

```text
financial-analysis
pdf-redline-review
wechat-copywriter
brand-slide-builder
```

避免：

```text
Financial Analysis
财务分析Skill
my_skill
skill-final-v2-new
```

命名原则：

- 短。
- 具体。
- 能看出主要能力。
- 必要时加平台或工具前缀。
- 技能包根目录名、`SKILL.md` 中的 `name`、压缩包语义尽量一致。

## 3. SKILL.md 标准结构

推荐使用以下结构：

```markdown
---
name: skill-name
description: |
  简要描述该 Skill 的能力和适用场景。
  Use when: (1) 场景一, (2) 场景二, (3) 场景三。
---

# Skill Name

## Purpose

说明该 Skill 的核心目标、解决的问题和最终交付价值。

## Instructions

1. 定义执行流程。
2. 定义使用资源的顺序。
3. 定义遇到不确定信息时如何处理。
4. 定义输出格式和验收标准。

## Resources

- `scripts/example.py`：什么时候使用，输入是什么，输出是什么。
- `references/knowledge.md`：什么时候读取，包含什么信息。
- `assets/template.png`：什么时候用于最终输出。

## Examples

输入：

用户请求示例。

输出：

期望结果摘要或结构。

## Guardrails

- 不做什么。
- 什么时候必须询问用户。
- 如何处理缺失数据。
- 如何避免安全、隐私、合规问题。
```

### 3.1 Frontmatter

Frontmatter 是 Skill 的触发入口。许多 Agent 只会先看到 `name` 和 `description`，正文只有在 Skill 被触发后才会加载。

因此：

- 触发条件必须写进 `description`。
- 不要把“什么时候使用本 Skill”只写在正文里。
- `description` 不要只写能力，也要写适用场景。

推荐格式：

```yaml
---
name: financial-analysis
description: |
  分析企业财务数据、财报、经营指标和风险信号，并生成结构化洞察。
  Use when: (1) 用户要求分析财报或财务指标，(2) 用户要求比较公司经营表现，(3) 用户要求识别收入、利润、现金流或偿债风险。
---
```

不推荐：

```yaml
---
name: analysis
description: |
  帮助用户分析问题，提高效率。
---
```

原因：过宽、过虚、触发边界不清，会导致误触发或漏触发。

### 3.2 Purpose

`Purpose` 只回答一个问题：这个 Skill 最终帮用户完成什么。

好的 Purpose：

```markdown
帮助用户基于企业财报、经营数据和行业背景，识别经营趋势、财务风险和可执行的分析结论。
```

差的 Purpose：

```markdown
这是一个很强大的财务分析助手，可以提升效率。
```

写作要求：

- 说明目标。
- 说明对象。
- 说明结果。
- 不写营销话术。

### 3.3 Instructions

`Instructions` 是 Skill 的执行骨架。

它应该告诉 Agent：

- 先做什么。
- 后做什么。
- 什么时候读取参考资料。
- 什么时候运行脚本。
- 什么时候询问用户。
- 如何处理异常。
- 最终输出什么格式。

推荐写成动词开头的步骤。

示例：

```markdown
1. 先识别用户任务类型：财报解读、公司对比、风险识别、指标计算或报告生成。
2. 如果用户没有提供数据来源，先询问需要分析的公司、时间范围和数据文件。
3. 如果用户提供表格或财报文件，优先提取收入、利润、现金流、资产负债和关键比率。
4. 对每个关键结论标明依据，不编造缺失数据。
5. 输出结构包括：摘要、关键发现、风险信号、需要补充的数据、下一步建议。
```

避免只写原则，不写动作。

不推荐：

```markdown
要专业、准确、全面地分析财务数据。
```

### 3.4 Resources

如果 Skill 有资源文件，必须在 `SKILL.md` 中说明“什么时候用”。

好的写法：

```markdown
- `references/industry-metrics.md`：当用户要求行业对比、指标解释或估值区间时读取。
- `scripts/calc_ratios.py`：当用户提供结构化财务表格并要求计算财务比率时运行。
- `assets/report-template.docx`：当用户要求生成正式报告时作为输出模板。
```

差的写法：

```markdown
参考资料在 references 里面。
```

原则：

- `SKILL.md` 只放导航和核心流程。
- 详细资料放 `references/`。
- 可执行逻辑放 `scripts/`。
- 输出素材放 `assets/`。
- 不要求 Agent 一开始读取所有资源。

### 3.5 Examples

示例的目标不是展示“看起来很厉害”，而是帮助 Agent 理解输入输出边界。

至少准备三类示例：

1. 标准成功示例。
2. 信息不足示例。
3. 边界或误用示例。

示例格式：

```markdown
输入：
请分析 A 公司 2021-2023 年财报，判断增长质量。

输出：
- 先提取三年收入、毛利率、净利率、经营现金流。
- 比较收入增长和利润增长是否匹配。
- 判断现金流是否支持利润质量。
- 输出风险和补充数据需求。
```

注意：

- 示例要贴近真实使用。
- 不要编造无法验证的数据。
- 输出可以写结构，不一定写完整长答案。

### 3.6 Guardrails

`Guardrails` 定义边界、限制和安全要求。

常见内容：

- 不编造数据。
- 不泄露密钥、隐私和敏感信息。
- 不执行危险操作。
- 数据不足时先询问或明确假设。
- 不把参考资料当成最终事实来源，必要时要求用户确认。
- 不承诺超出能力范围的结果。

示例：

```markdown
- 不编造财务数据；缺失字段必须标明“未提供”。
- 不给出确定性投资建议；只能输出分析和风险提示。
- 如果用户上传的数据存在口径冲突，先列出口径差异，再继续分析。
- 不在输出中暴露任何 API key、账号、cookie 或内部路径。
```

## 4. 渐进式披露原则

Skill 的信息加载应该分层。

| 层级 | 内容 | 目标 |
| --- | --- | --- |
| 第 1 层 | `name` + `description` | 让 Agent 判断是否触发 |
| 第 2 层 | `SKILL.md` 正文 | 给出核心流程和资源导航 |
| 第 3 层 | `scripts/`、`references/`、`assets/` | 按需加载或使用详细资源 |

核心原则：

- `description` 负责触发。
- `SKILL.md` 负责执行导航。
- `references/` 负责承载长资料。
- `scripts/` 负责确定性执行。
- `assets/` 负责最终产物素材。

当 `SKILL.md` 越来越长时，不要继续堆内容，应拆分：

```text
references/
├── api.md
├── examples.md
├── faq.md
└── edge-cases.md
```

拆分后必须在 `SKILL.md` 里写清楚：

- 文件里有什么。
- 什么时候读取。
- 适用于哪些任务。

避免深层跳转。参考文件最好都从 `SKILL.md` 直接链接，不要让 Agent 在多级文档中寻找线索。

## 5. 自由度设计原则

写 Skill 时要决定：哪些地方让 Agent 自主判断，哪些地方必须固定。

### 5.1 高自由度：用文字规则

适用场景：

- 文案写作。
- 咨询分析。
- 策略建议。
- 需要结合上下文判断的任务。

写法：

```markdown
根据用户行业、目标受众和渠道选择语气；如果用户未指定渠道，先按公众号长文场景处理。
```

### 5.2 中自由度：用步骤或伪代码

适用场景：

- 有稳定流程，但细节可变。
- 需要参数选择。
- 需要分支判断。

写法：

```markdown
1. 判断输入类型。
2. 如果是 CSV，读取表头并推断字段含义。
3. 如果是 PDF，先提取文字，再识别表格。
4. 如果字段缺失，列出缺失项并询问用户。
```

### 5.3 低自由度：用脚本

适用场景：

- 文件转换。
- 数据清洗。
- 批量处理。
- 公式计算。
- 渲染导出。
- 容易因手写代码出错的任务。

写法：

```markdown
当用户提供结构化财务表格并要求计算财务比率时，运行 `scripts/calc_ratios.py`，不要临时重写计算逻辑。
```

原则：

- 越脆弱的流程，越要脚本化。
- 越依赖上下文判断的流程，越要保留 Agent 自由度。
- 不要把所有东西都写死，也不要把关键可靠性全部交给临场发挥。

## 6. TRACE 五原则质量框架

TRACE 是评估 Skill 质量的五个维度：

| 维度 | 中文 | 核心问题 |
| --- | --- | --- |
| T - Trust | 信任 | 用着放心吗？ |
| R - Reliability | 可靠性 | 每次都稳吗？ |
| A - Adaptability | 适用性 | 该出手时出得来吗？ |
| C - Convention | 规范性 | 写得清楚、改得动吗？ |
| E - Effectiveness | 有效性 | 最终交付结果好用吗？ |

五个维度是因果链：

Trust 是地基，Reliability 是承重墙，Adaptability 是触发和适配，Convention 是工程图纸，Effectiveness 是最终交付体验。

### 6.1 T - Trust 信任

目标：用户敢用，平台敢推荐，维护者敢接手。

检查点：

- 是否包含可疑代码、命令注入风险或危险操作。
- 是否硬编码 API key、账号、cookie、token、内部地址。
- 是否可能泄露用户上传的隐私或业务数据。
- 是否说明了敏感数据处理方式。
- 是否支持中文交互。
- 是否能在目标网络环境下运行。
- 是否对依赖的外部服务、API、平台限制有说明。

高质量表现：

- 不存储、不暴露敏感信息。
- 脚本参数经过校验。
- 危险操作需要用户明确确认。
- 对外部依赖有替代方案或失败提示。
- 对国内常用工具链和中文场景有适配说明。

常见问题：

- 在示例中写入真实密钥。
- 脚本直接拼接用户输入执行系统命令。
- 完全依赖不可访问的海外服务。
- 对隐私数据处理没有边界。

### 6.2 R - Reliability 可靠性

目标：同类任务反复执行，结果稳定。

检查点：

- 功能描述中承诺的能力是否都能实际完成。
- 脚本是否经过测试。
- 输入参数是否有校验。
- 是否有默认值、重试、超时、失败恢复策略。
- 是否处理空值、超长文本、特殊字符、格式不一致等异常。
- 错误信息是否能指导用户修正。

高质量表现：

- 标准输入可以稳定成功。
- 非标准输入能给出友好提示。
- 失败时说明原因和下一步。
- 输出结构稳定。

常见问题：

- 描述写了五个功能，实际只能做一个。
- 用户输入稍微变化就失效。
- 报错信息只有底层异常。
- 缺少验证步骤。

### 6.3 A - Adaptability 适用性

目标：该触发时触发，不该触发时不误用。

检查点：

- `description` 是否明确写出能力和触发场景。
- 是否说明了不适用场景。
- 是否覆盖用户可能使用的关键词和表达方式。
- 范围是否过宽或过窄。
- 是否有正向示例和反向示例。

高质量表现：

- 用户看完就知道什么时候该用。
- Agent 能根据 `description` 正确命中。
- 对相邻能力有边界说明。

常见问题：

- `description` 写成“提升效率”“辅助分析”等泛化表述。
- 触发条件只写在正文，导致 Skill 无法被发现。
- 能力边界模糊，导致误触发。

### 6.4 C - Convention 规范性

目标：写得清楚、放得合理、后续改得动。

检查点：

- 目录结构是否符合规范。
- `SKILL.md` 是否结构清晰。
- 资源文件命名是否一致。
- 长资料是否拆到 `references/`。
- 示例是否真实可用。
- 是否包含常见反模式和 FAQ。
- 三个月后他人接手，是否能快速理解。

高质量表现：

- `SKILL.md` 不臃肿。
- 资源按需披露。
- 命名统一。
- 示例与真实任务贴近。
- 维护者能快速定位修改点。

常见问题：

- 把所有文档都塞进 `SKILL.md`。
- 资源文件存在但没有说明用途。
- 目录命名混乱。
- 示例是随便编的，不能指导使用。

### 6.5 E - Effectiveness 有效性

目标：用户用了以后，问题真的被解决，而且结果可直接使用。

检查点：

- 输出是否准确。
- 逻辑是否自洽。
- 是否覆盖用户需求的全部关键部分。
- 输出格式是否符合预期。
- 是否减少用户二次加工成本。
- 是否提供额外洞察、建议或整合价值。

高质量表现：

- 结果能直接交付或继续使用。
- 不只完成表层任务，还补上关键判断。
- 对复杂任务能保持完整性。

常见问题：

- 输出看似完整，但没有解决核心问题。
- 忽略用户约束。
- 给出大量泛泛建议。
- 需要用户重新整理才能使用。

## 7. TRACE 评分表

每个维度按 1-5 分评分。

| 分数 | 标准 |
| --- | --- |
| 1 | 存在明显问题，不建议使用 |
| 2 | 勉强可用，但风险或缺陷明显 |
| 3 | 达到基础合格线 |
| 4 | 质量较高，可稳定复用 |
| 5 | 优秀，可作为同类 Skill 标杆 |

发布建议：

| 总体情况 | 处理建议 |
| --- | --- |
| 任一维度低于 3 分 | 不建议发布，先修复短板 |
| Trust 低于 4 分 | 不建议公开推荐 |
| Reliability 低于 3 分 | 必须补测试和异常处理 |
| Adaptability 低于 3 分 | 重写 `description` 和边界说明 |
| Convention 低于 3 分 | 重构目录和文档 |
| Effectiveness 低于 3 分 | 回到真实任务样例重新设计 |

评审模板：

```markdown
## TRACE 评审

- Trust：/5
- Reliability：/5
- Adaptability：/5
- Convention：/5
- Effectiveness：/5

主要问题：
1.
2.
3.

优先修复：
1.
2.
3.

是否建议发布：
```

## 8. Skill 编写流程

推荐按以下顺序创建或升级 Skill。

### Step 1：定义任务边界

先回答：

- 这个 Skill 解决哪一类任务？
- 不解决哪一类任务？
- 用户通常会怎么提出需求？
- 最终交付物是什么？
- 任务失败通常因为什么？

输出：

```markdown
能力范围：
不适用范围：
典型用户请求：
最终输出：
主要风险：
```

### Step 2：收集真实样例

至少准备 3-5 个样例：

- 标准请求。
- 信息不足请求。
- 边界请求。
- 容易误触发的相邻请求。
- 高价值复杂请求。

不要只用理想样例。好的 Skill 必须覆盖真实输入的混乱性。

### Step 3：设计触发描述

先写 `description`，再写正文。

`description` 必须包含：

- 这个 Skill 做什么。
- 什么时候用。
- 面向哪些输入或任务。
- 可选：不适合什么任务。

模板：

```yaml
description: |
  [能力概述]。
  Use when: (1) [明确场景一], (2) [明确场景二], (3) [明确场景三]。
  Do not use when: [容易误触发的相邻场景]。
```

### Step 4：设计执行流程

把真实任务拆成稳定步骤。

推荐结构：

```markdown
1. 识别任务类型。
2. 检查输入是否足够。
3. 按需读取参考资料或运行脚本。
4. 执行核心分析或生成。
5. 校验输出。
6. 按指定格式交付。
```

每一步都尽量写清楚：

- 输入是什么。
- 判断标准是什么。
- 用什么资源。
- 输出什么中间结果。
- 失败时怎么办。

### Step 5：决定资源放置

使用以下判断：

| 内容类型 | 放置位置 |
| --- | --- |
| 核心流程 | `SKILL.md` |
| 大段业务知识 | `references/` |
| API 文档、schema、规则表 | `references/` |
| 可执行计算、转换、渲染 | `scripts/` |
| 模板、图标、字体、图片 | `assets/` |
| 真实输入输出案例 | 简短放 `SKILL.md`，长案例放 `references/examples.md` |

### Step 6：写 Guardrails

从 Trust 和 Reliability 两个角度写边界。

必须考虑：

- 数据是否敏感。
- 是否会造成误导。
- 是否会修改文件、发请求、调用 API。
- 是否可能输出不确定事实。
- 是否需要用户确认。

### Step 7：本地自检

发布前至少检查：

- `SKILL.md` 是否存在。
- YAML frontmatter 是否完整。
- `name` 是否规范。
- `description` 是否清楚。
- 所有资源路径是否存在。
- 脚本是否能运行。
- 示例是否能覆盖真实场景。
- TRACE 每项是否至少 3 分。

### Step 8：真实任务测试

用真实请求测试，而不是只读文档。

测试集至少包含：

```markdown
1. 正常任务：应该完整成功。
2. 信息不足：应该询问或列出缺口。
3. 边界任务：应该明确拒绝或转向。
4. 异常输入：应该友好处理。
5. 复杂任务：应该保持输出完整性。
```

### Step 9：迭代优化

每次使用后记录：

- Agent 是否正确触发。
- 哪一步卡住。
- 哪些资料被重复查找。
- 哪类输出需要返工。
- 用户是否还要补充说明。

按 TRACE 顺序修复：

1. 先修 Trust。
2. 再修 Reliability。
3. 再修 Adaptability。
4. 再修 Convention。
5. 最后提升 Effectiveness。

## 10. 示例：financial-analysis

```markdown
---
name: financial-analysis
description: |
  分析企业财务数据、财报指标、经营趋势和风险信号，并生成结构化财务洞察。
  Use when: (1) 用户要求分析公司财报，(2) 用户要求比较多家公司财务表现，(3) 用户要求识别收入、利润、现金流、负债或经营风险。
  Do not use when: 用户要求确定性股票买卖建议、预测股价或编造未提供的财务数据。
---

# Financial Analysis

## Purpose

帮助用户基于企业财报、经营数据和行业背景，识别经营趋势、财务质量、潜在风险和可执行的分析结论。

## Instructions

1. 先识别用户任务类型：财报解读、公司对比、风险识别、指标计算或报告生成。
2. 如果用户没有提供数据来源，询问公司名称、时间范围、财报文件或关键指标。
3. 如果用户提供结构化表格，提取收入、毛利率、净利率、经营现金流、资产负债和关键比率。
4. 如果用户提供 PDF 或非结构化材料，先提取文字和表格，再标注数据来源。
5. 分析收入增长、利润质量、现金流匹配、偿债压力和异常变化。
6. 对每个结论说明依据；数据不足时标明缺口。
7. 输出摘要、关键发现、风险信号、需要补充的数据和下一步建议。

## Resources

- `references/finance-metrics.md`：当需要解释财务指标、计算口径或风险阈值时读取。
- `scripts/calc_ratios.py`：当用户提供结构化财务表格并要求计算比率时运行。
- `assets/report-template.docx`：当用户要求生成正式分析报告时使用。

## Examples

输入：

请分析 A 公司 2021-2023 年财报，判断增长质量。

输出：

- 摘要：收入、利润和现金流整体趋势。
- 关键发现：增长驱动因素和异常变化。
- 风险信号：利润质量、现金流、负债压力。
- 数据缺口：缺失或需确认的指标。
- 下一步建议：建议补充的数据或分析方向。

## Guardrails

- 不编造未提供的财务数据。
- 不给出确定性投资建议。
- 数据口径冲突时，先列出口径差异。
- 如果缺少关键数据，先说明限制或询问用户。
- 不输出任何密钥、账号、cookie 或敏感路径。

## Validation

交付前检查：

- 每个核心结论是否有数据依据。
- 是否区分事实、推断和建议。
- 是否标明缺失数据和不确定性。
- 输出是否能被用户直接用于下一步分析。
```

## 11. 常见反模式

### 11.1 描述过宽

问题：

```yaml
description: 帮助用户完成各种分析任务。
```

后果：

- 容易误触发。
- Agent 不知道具体能力。
- 用户预期失控。

修复：

```yaml
description: |
  分析企业财务数据、财报指标和经营风险，并生成结构化财务洞察。
  Use when: (1) 财报分析, (2) 公司对比, (3) 财务风险识别。
```

### 11.2 把正文当触发器

问题：

```markdown
## 使用场景
当用户要分析财报时使用。
```

但 `description` 没写触发场景。

后果：

- Agent 可能根本不会加载正文。

修复：

- 把触发条件写进 `description`。
- 正文可以补充说明，但不能依赖正文触发。

### 11.3 SKILL.md 过长

问题：

- 把 API 文档、行业知识、FAQ、长案例全部塞进 `SKILL.md`。

后果：

- 加载成本高。
- 重点不清。
- 维护困难。

修复：

- 核心流程留在 `SKILL.md`。
- 长资料拆到 `references/`。
- 在 `SKILL.md` 中写清楚何时读取。

### 11.4 有资源但没导航

问题：

```text
references/
├── doc1.md
├── doc2.md
└── final.md
```

但 `SKILL.md` 没写这些文件用途。

后果：

- Agent 不知道什么时候读。
- 资源利用率低。

修复：

```markdown
- `references/doc1.md`：用于 A 场景。
- `references/doc2.md`：用于 B 场景。
- `references/final.md`：用于输出最终报告前核对格式。
```

### 11.5 只有原则，没有流程

问题：

```markdown
要准确、专业、全面、结构化。
```

后果：

- 每次执行都靠临场发挥。
- 结果不稳定。

修复：

- 写成明确步骤。
- 加输入检查。
- 加输出格式。
- 加验证清单。

### 11.6 示例脱离真实任务

问题：

- 示例过短。
- 示例没有边界。
- 示例输出无法指导 Agent。

修复：

- 用真实用户请求。
- 加信息不足和误用示例。
- 输出结构而不是空泛描述。

### 11.7 缺少失败处理

问题：

- 没写数据缺失怎么办。
- 没写外部服务失败怎么办。
- 没写格式不兼容怎么办。

修复：

```markdown
如果输入数据不足，先列出缺失字段，并询问用户是否继续基于已有数据做有限分析。
```

## 13. 既有 Skill 的升级方法

升级旧 Skill 时，不要一上来重写全文。先诊断，再修复。

### 13.1 诊断顺序

按 TRACE 顺序检查：

1. Trust：有没有安全、隐私、依赖和环境风险。
2. Reliability：是否稳定，异常是否可处理。
3. Adaptability：触发是否准确，边界是否清晰。
4. Convention：结构是否清楚，资源是否合理。
5. Effectiveness：最终结果是否真的好用。

### 13.2 修复优先级

优先修阻断问题：

- 泄露敏感信息。
- 危险操作。
- 脚本不可运行。
- 触发条件缺失。
- 核心流程缺失。

再修质量问题：

- 示例不足。
- 输出格式不稳定。
- 资源组织混乱。
- 缺少验证步骤。

最后做增强：

- 增加高级案例。
- 增加脚本自动化。
- 增加模板素材。
- 增加复杂边界处理。

### 13.3 升级记录模板

```markdown
## Skill 升级记录

Skill：
日期：

原主要问题：
- Trust：
- Reliability：
- Adaptability：
- Convention：
- Effectiveness：

本次修改：
1.
2.
3.

测试样例：
1.
2.
3.

剩余风险：
```

## 14. 最终交付标准

一个 Skill 达到以下标准，才算可以稳定复用：

- 用户知道什么时候该用。
- Agent 能正确触发。
- 执行步骤清楚。
- 资源按需加载。
- 异常有处理方式。
- 输出结构稳定。
- 不编造、不泄露、不越界。
- 结果能直接使用。
- 后续维护者能快速修改。

最小合格标准：

```text
格式正确 + 触发清晰 + 流程可执行 + 边界明确 + TRACE 每项 >= 3
```

优秀标准：

```text
触发精准 + 结果稳定 + 资源分层 + 脚本可靠 + 示例真实 + TRACE 每项 >= 4
```

标杆标准：

```text
能覆盖复杂真实场景 + 输出明显优于通用 Agent + 可被他人复用和扩展 + TRACE 每项接近 5
```

## 16. 一句话复盘

写 Skill 的目标不是把所有知识塞进去，而是让 Agent 在正确的场景下，用最少但足够的信息，稳定地产出可直接使用的结果。

用 TRACE 看质量：

```text
Trust 决定能不能用。
Reliability 决定能不能反复用。
Adaptability 决定能不能用对。
Convention 决定能不能维护。
Effectiveness 决定值不值得用。
```
