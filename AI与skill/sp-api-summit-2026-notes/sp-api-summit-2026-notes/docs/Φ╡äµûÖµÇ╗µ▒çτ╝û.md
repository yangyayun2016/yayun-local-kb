### 1.3 三条主线

1. **接口把订单、商品、履约和经营数据连接起来。**
2. **AI 与 MCP 帮开发者理解、调用和迁移接口。**
3. **运营分析需要把店铺整体表现与广告表现放在一起看。**

对运营新人，最有价值的不是背接口名称，而是知道 ERP 能解决哪些问题、数据是否完整，以及可以向技术人员提出什么具体需求。

### 1.4 最需要保留的四个判断

1. **读取能力与写入能力分开看。** 促销读取已发布的现场口径，不等于创建更新也已开放。
2. **AI 输出要回到版本与测试。** 迁移演示有明确的预发布提示，与另一页版本不同，不能直接上线照用。
3. **数据连接要先统一口径。** 站点、时间、币种、粒度和归因窗口对不上，漂亮的统一看板也可能误导运营。
4. **API 接入包含持续维护。** 同步、分页、错误处理、权限、删除与测试，都是软件可用性的一部分。

### 1.5 核心结论

现有测试记录已覆盖官方 MCP 安装与库存读取、部分订单与财务查询，以及一次 Data Kiosk 销售汇总工作流和后台对账。它们证明了**具体链路可以跑通**；完整利润、广告优化和长期自动化仍需要更多数据、权限与运行保障。

## 3 业务接口分主题

### 3.1 Orders 订单

#### 新 GET 工作流【现场 IMG_2331】

- 操作名称：`SearchOrders`
- 路径：`/orders/2026-01-01/orders`
- 筛选维度：创建时间前后、最近更新时间前后、订单状态、商城 ID、履约渠道（FBM/FBA）、包含的数据集

标题强调"流程统一，一次调用获取全部信息"。**【解读】** 以前需要分开查询订单、买家、地址、包裹再拼接；新方向是按需获取更完整的订单对象。但"一次调用"是演示表达，不能理解成任意数量的订单都不用分页或补充查询。权限、分页和业务状态限制依然存在。

#### 代码演示中的字段变化【现场 IMG_2333】

Python 演示注释为 "Orders API 2026-01-01"、"1 call per order | no RDT"，用 `included_data` 请求 `BUYER`、`RECIPIENT`、`PROCEEDS`、`PACKAGES`。

| 演示所列变化 | 对开发工作的含义 |
|---|---|
| `fulfillment_channels` → `fulfilled_by`，`MFN` → `MERCHANT` | 请求字段与枚举需重新映射 |
| `order_statuses` → `fulfillment_statuses`，`Unshipped` → `UNSHIPPED` | 状态拼写及大小写不可直接沿用 |
| 去掉 `payload` 外层 | 旧响应解析代码可能需要调整 |
| `amazon_order_id` → `order_id` | 订单标识字段的读取方式需核对 |
| `included_data` 按需获取多类信息 | 数据选择与应用权限需要一起检查 |
| PII 由应用角色限制，不再往返获取 RDT | "不需要 RDT"不表示任何应用都能获取敏感信息 |

> **同组照片存在表达差异【待核实 Q04】**
> IMG_2331 示例使用 `status=Unshipped`（幻灯片 URL 示例），IMG_2333 使用 `fulfillment_statuses=["UNSHIPPED"]`（Python 演示）。不要拼接成一段未经验证的可运行请求；最终参数按实际采用版本的接口定义核对。

**PII** 是可识别个人的信息；**RDT** 是 Restricted Data Token（受限数据令牌）。新 Orders 不要求额外 RDT，不代表所有 SP-API 都取消 RDT【待核实 Q05】。

#### 对运营的实际影响【解读】

可向 ERP 团队提出的需求：订单同步能否同时带出企业购标识、PO、收货公司、金额与包裹；同步失败是否有提示；更新后的订单能否重复抓取而不重复建单。

验收时更应看"有没有漏单、重复单、缺地址或丢包裹"，而不只看接口是否返回成功。

参考：[Orders API v2026-01-01 发布公告](https://developer-docs.amazon/sp-api/changelog/new-introducing-the-orders-api-v2026-01-01) · [迁移指南](https://developer-docs.amazon/sp-api/docs/orders-api-migration-guide)

### 3.2 Listings 商品

**Listing** 是卖家在某站点的商品刊登信息；**Marketplace** 是具体销售市场；**ASIN** 是亚马逊商品标识；**SKU** 是卖家管理编码。

#### 同一区域多商城检索【现场 IMG_2349】

`getListingsItem` 与 `searchListingsItems`：

1. 可接受**同一区域**的多个商城 ID，一个请求检索多个商城的商品信息。
2. 响应可包括概要、报价、属性与问题；各项带商城 ID，便于识别来源。
3. 可减少对同一商品逐站点连续调用。
4. 对单商城请求保持向后兼容。
5. **仅适用于卖家**；投影片说明供应商代码映射至单一商城。
6. `searchListingsItems` 的筛选与排序（如 `withStatus`、`sortBy`）按第一个 ID（主商城）评估。

> **容易踩的坑：** 返回多个站点的数据，不等于每个站点都独立执行了一次相同筛选；第一个商城 ID 的选择会影响查询结果。也不能把"同一区域"扩展为任意跨区域组合。报表中必须保留站点维度。

#### 运营场景【解读】

适合建立同一 SKU 在多个站点的属性、报价与问题清单。报表至少保留"卖家／账号、站点、SKU、ASIN、问题类型、抓取时间"，避免不同站点覆盖彼此。

议程主题是"首次提交即成功上架 ASIN"，但本批没有完整的商品类型要求、提交前校验、问题修复与发布结果页，**因此不重建一套声称来自现场的完整上架 SOP**【待核实 Q18】。

资源照片 IMG_2352 展示 `linktr.ee/amzn_listing`，另有"管理商品信息问题""管理可售商品"两个二维码，链接内容尚未访问。

### 3.3 Promotions 促销

#### 能力地图【现场 IMG_2363】

四类：卖家／供应商级数据、促销状态、筛选条件、多种促销类型。

- 可同步促销当前状态
- 按促销类型、ASIN、日期范围、修订版类型筛选
- 促销类型包括优惠、优惠券、价格折扣、购物篮构建

"购物篮构建"可理解为鼓励买家凑单或满足组合购买条件，例如满一定金额减免。准确资格仍要看活动条件。

#### 三个读取操作【现场 IMG_2364】

| 操作 | 现场说明 | 可以回答的问题 |
|---|---|---|
| `searchPromotions` | 按条件搜索，分页返回摘要：标题、预算、起止日期、状态、优惠力度、促销 ID、商城 | 有哪些活动，处于什么状态？ |
| `getPromotion` | 获取指定促销 ID 的完整数据及促销验证问题 | 某个活动为什么可能有问题？ |
| `getProductSelection` | 分页返回商品选择详情、专属优惠、商品级验证问题，支持超过 100 件商品 | 活动里哪些商品参与，哪些有问题？ |

> **应用建议【解读】：** 活动级"正常"不代表每件商品都无问题；运营看板要能从活动摘要下钻到商品选择。超过 100 件商品的场景尤其应检查分页是否全部读取。

**写入能力边界：** 创建更新在会场被列为未来计划（私测 2026 年底、正式 2027 年初），本批没有完成写入测试。**不能从读取可用推导出当前可以批量修改活动**【待核实 Q06、Q07】。

参考：[Promotions API](https://developer-docs.amazon/sp-api/docs/promotions-api)

### 3.4 Pricing 定价：竞争摘要与 FOEP

#### getCompetitiveSummary 新增两个数据点【现场 IMG_2368】

**Similar Items（相似商品）** 与 **Promotions（促销）**。

**优惠券示例（IMG_2369）：** 商品展示价 99.99 美元，45% 优惠券；字段 `percentageOff: 45.0`、`type: PERCENTAGE_OFF`、折后价 `54.99 USD`、`promotionType: COUPON`。

**购物篮示例（IMG_2371）：** 标价 14.79 美元，符合条件的商品购买满 30 美元减 5 美元；字段 `promotionType: BASKET_BUILDING`、`AMOUNT_OFF`、`amountOff` 为 5 USD、购买门槛 `AT_LEAST` 为 30 USD。

> **判断标准：** 分析价格竞争力时需同时看优惠形式和满足条件。满 30 减 5 不能直接理解为每件商品减 5；优惠券也不能假设所有买家都已领取、适用或与其他活动叠加。金额仅为会议示例，不是当下商品报价。

#### FOEP 推荐报价预期价格【现场 IMG_2372–2373】

**FOEP（Featured Offer Expected Price）** 用于评估争取 Featured Offer（推荐报价，运营常称购物车）时的价格参考。**没有承诺按该价格设置就一定获得购物车。**

- 操作：`getFeaturedOfferExpectedPriceBatch`
- 路径：`/batches/products/pricing/2022-05-01/offer/featuredOfferExpectedPrice`
- 每个请求最多 40 个 SKU
- 输入：商城编号、SKU、位置（可选）
- 返回示例含 `featuredOfferExpectedPrice`、`competingFeaturedOffer`、`currentFeaturedOffer`；示例状态 `VALID_FOEP`

| 用例 | 现场描述的方向 | 业务检查【解读】 |
|---|---|---|
| 自动调价 | 将价格设为等于或低于 FOEP，提高获得推荐报价的概率 | 要同时检查可接受利润与最低售价 |
| 价格竞争分析 | 了解目录中商品获得推荐资格的价格限额 | 注意站点、配送条件和查询时点 |
| 商品组合优化 | 按 FOEP 差值确定优先重新定价的 ASIN | 差值大不一定值得降价，还要看需求与利润 |
| 定价提醒 | 重要商品的 FOEP 大幅变化时通知卖家 | 先确认变化持续性，再决定动作 |

满额优惠不能逐件直接扣减，按参考价格调价也不保证取得购物车。

#### 财务数据能辅助对账，不能单独算出完整净利润

采购、头程、包装、税务处理、汇率、站外成本及广告消耗分摊需要补齐。**订单净额不等于利润；费用优惠抵扣到零不等于费用永久取消。**

按首次记账分析经营收支与按释放日期分析现金流，是两种不同报表。出现 `DEFERRED_TRANSACTION_ID`、`RELEASE_TRANSACTION_ID` 等关联时，要核验原始交易与释放交易的关系，避免重复计收入；**也不能无条件删除所有释放记录**，因为原始交易可能在其他期间。

`listTransactions` 官方提示可能未包含最近 48 小时的订单财务记录。这是完整性与时效限制，**不能扩展为"所有财务接口都延迟 48 小时"或"48 小时内金额必然错误"**。分页要读到结束，空页也可能仍有下一页。

#### 可用、暂缓和到账

余额可能包含 AVAILABLE（可用）、RESERVED（预留）及其下层 DEFERRED（暂缓）、ACCOUNT_LEVEL_RESERVE（账户级预留）。**核对层级后再求和，不能把父项与子项重复相加。**

暂缓的常见原因包括配送日期预留 DD7 以及企业买家账期 B2B。DD7 通常与送达后预留期有关，不是等待买家手动点击确认收货；企业账期则可能等待买家支付发票。**预计释放日期不是银行到账日期。**

资金通常经历"暂缓 → 释放 → 纳入结算付款 → 银行到账"。余额少不等于违规冻结。费用支付还取决于卖家扣款方式及广告账单设置；负余额不代表无限赊账，付款失败可能影响广告或账户使用。具体应核对到期账单、备用付款方式和后台通知，而不是仅凭余额判断。

参考：[暂缓交易说明](https://sellercentral-europe.amazon.com/seller-forums/discussions/t/3fe1fff3-f924-42bc-aa45-69244e8d6f83) · [广告付款方式说明](https://advertising.amazon.com/library/news/update-on-advertiser-payments) · [负余额处理说明](https://sellercentral.amazon.com/seller-forums/discussions/t/6e57e55b-9a25-4a8e-a6cd-e837040ec33f)

| SP-API 销售 | `orderedProductSales`、`netProductSales`、`averageSellingPrice` | 整体订购、净销售与平均售价 |
| SP-API 流量 | `sessions`、`pageViews`、`buyBoxPercentage` | 会话、浏览、购物车占比 |
| Ads API 标识 | `advertisedAsin`、`advertisedSku`、`campaignName`、`adGroupName` | 广告推广的商品与投放路径 |
| Ads API 表现 | `impressions`、`clicks`、`cost`、`sales7d`、`orders7d` | 展示、点击、花费及 7 天归因销售与订单 |

补充照片 `B02-01_统一分析表.jpg` 是同一页更完整的一张，左侧字段清单与右侧统一输出框在同一画面内，可用于核对上表字段是否抄全。IMG_2412 的统一输出写了：自然销量 = 总销量 − 广告销量；TACoS = 广告支出 ÷ 总销售额；从展示到点击、从会话到购买贯穿付费与自然渠道。

> **会议中的简化公式，需要口径校验后才能用于真实店铺【待核实 Q15】**
> `orders7d` 是订单指标，不能直接当作销量件数；`sales7d` 是广告归因销售额，不能直接与任意净销售额相减。订单日期与广告归因日期、退款处理、币种、站点、归因窗口及跨商品归因都可能不同。未对齐前，"总量减广告量"最多保留为**待验证差额**，不能命名为准确的自然销量，也不能据此证明广告带来的增量。

**ACoS 的分母是广告归因销售额，TACoS 的分母是整体销售额。** 订单数、件数、订购销售额、净销售额和投放日／归因日不能混算。

SP-API 授权成功不等于广告授权成功。欧洲 SP-API 与 Ads API 地址分别是 `sellingpartnerapi-eu.amazon.com` 和 `advertising-api-eu.amazon.com`；后者的账户列表请求还需要广告鉴权。

## 4 AI · MCP · 工作流

### 4.1 五个组件各负责什么

| 组件 | 白话解释 | 例子 |
|---|---|---|
| AI Agent | 理解需求、选择工具并解释结果的助手 | 理解"查昨天销售，再对账" |
| MCP | AI 与工具沟通的协议 | 把查询需求交给外部工具 |
| SP-API | 亚马逊业务接口体系 | 读取库存、订单、财务 |
| Reports API | 按预设类型生成或读取报表 | 获取促销效果报表 |
| Data Kiosk | 在支持的数据集中按字段和条件查询 | 只取某完整日期的销售汇总 |

官方 Local MCP 包含两个可独立使用的服务器：**开发助手**负责找接口和发起请求；**工作流服务器**负责保存及运行多个步骤。它们是官方集成示例，生产使用仍需团队测试、维护与权限控制。

### 4.2 开发助手的六个工具

| 工具 | 主要用途 |
|---|---|
| `sp_api_reference` | 检索官方文档 |
| `sp_api_explore_catalog` | 查看路径、参数、响应结构与目录 |
| `sp_api_execute` | 执行获授权的真实业务请求 |
| `sp_api_generate_code_sample` | 辅助生成 SDK 代码示例 |
| `sp_api_migration_assistant` | 分析版本迁移与代码变化 |
| `sp_api_optimize` | 检查分页、限流、缓存及错误处理等集成问题 |

### 4.3 工作流如何运行

**链路：** 业务目标 → AI 查接口与参数 → 创建或复用 JSON → 校验流程 → 本地执行器调用接口 → 保存结果与日志 → AI 解释结果。

JSON 用状态和转移规则描述步骤；**ASL** 是 Amazon States Language。本地工作流服务器使用 Node.js 执行器，提供等待、分支、文件获取、暂停恢复和人工输入等工具。某批连接记录发现 30 个工具，这只是该版本的观察值。

**Data Kiosk 查询是异步的：** 创建查询 → 等待完成 → 获取文档下载地址 → 下载 JSONL 文件。JSONL 每行是一条 JSON 数据，便于逐条解析。**提交成功只表示任务已受理**，不能代替完成状态和文件内容校验。

> **本地 JSON 与云端 JSON 不一定通用。**
> 官方云端示例使用 AWS Step Functions 调度 Lambda；本地执行器支持的任务资源不同。测试中 AWS 示例原样导入成功，但运行时因不支持 Lambda 资源而失败，适配成本地任务后才跑通。

已有流程可查找、查看定义、导入、校验和执行。导出 Mermaid 流程图或独立 Node.js 脚本的能力通过工具及源码确认，但**没有单独执行导出脚本**。保存流程也不会自动创建每日定时任务。

## 5 接入与授权

### 5.1 本地 MCP 不是一个公网网址

npm 是软件安装渠道。这个 MCP 在**本机启动**，通过 stdio（标准输入输出）与 AI 客户端通信，再通过 HTTPS 请求亚马逊。因此无需先申请公网 MCP 地址。本地运行仍需联网；数据进入 AI 客户端后如何处理，取决于所用平台及设置。

以下为本批测试使用的固定版本示例，不表示该版本永远最新。运行环境为 Node.js 20 或以上。

```bash
npm install -g @amazon-sp-api-release/sp-api-dev-mcp@1.0.5

# 开发助手
sp-api-dev-assistant-mcp-server

# 工作流服务器
sp-api-workflow-mcp-server
```

也可以不全局安装，直接在 MCP 客户端里用 `npx -y` 调起；完整客户端配置示例见 4.8。

### 5.2 环境变量（仅列含义，不附真实凭证）

| 配置 | 用途 |
|---|---|
| `SP_API_CLIENT_ID` | 应用客户端编号 |
| `SP_API_CLIENT_SECRET` | 对应应用密钥 |
| `SP_API_REFRESH_TOKEN` | 卖家授予该应用的长期授权凭证 |
| `SP_API_REGION` | 按实际区域选 na、eu 或 fe |
| `SP_API_BASE_URL` | 对应区域的公开 API 地址 |

**`NPM_TOKEN` 属于发布软件包到 npm 的流程**，普通用户安装公开包不需要申请；它不是店铺授权令牌。

### 5.3 应用编号和令牌不要混用

| 概念 | 作用 |
|---|---|
| Application ID | 标识 SP-API 应用 |
| Client ID / Client Secret | 识别 OAuth 客户端 |
| Refresh Token | 特定卖家给该客户端的授权 |
| Access Token | 调用时使用的短期令牌 |

**LWA（Login with Amazon）** 是亚马逊的授权实现。建立安全配置文件不会自动获得卖家业务权限，刷新令牌也不能跨客户端混用。测试中曾出现 `unauthorized_client`，更换为对应应用凭证后成功换取访问令牌；**单看错误码不能判定所有同类失败都出于同一个原因。**

### 5.4 自授权和公共应用授权

| 方式 | 适合场景 | 关键步骤 |
|---|---|---|
| 自授权 | 自己有资格授权的账号进行接入测试 | 在应用管理中授权，安全保存刷新令牌 |
| 公共应用 OAuth | 让其他卖家接入自己的应用 | 注册登录与回调地址，验证 state，及时兑换授权码，按卖家隔离令牌和数据 |

公共应用可用自授权测试；但**自授权成功不等于网站回调已通过验证**。其他卖家不需要获得开发者的 Client Secret。回调网址背后必须有处理程序，仅填一个地址不构成完整授权服务。

刷新令牌是长期、可撤销的凭证；公共应用还涉及定期重新授权要求，不能承诺永久有效。自动换取 Access Token 也不等于可以自动恢复已撤销的卖家授权。

参考：[自授权](https://developer-docs.amazon/sp-api/docs/self-authorization)（当前页面标题为 Authorize Private Applications）· [公共应用授权](https://developer-docs.amazon/sp-api/docs/authorize-public-applications) · [重新授权](https://developer-docs.amazon/sp-api/docs/renew-authorizations)

### 5.5 身份与权限辨别

| 概念 | 白话解释 | 如何确认 |
|---|---|---|
| Seller 第三方卖家 | 通过平台向消费者销售 | Seller Central 后台及卖家业务授权 |
| Vendor 供应商 | 向亚马逊供货，由亚马逊零售 | Vendor Central 供应商合同和采购订单 |
| SPN 服务商网络 | 面向卖家提供服务的机构网络 | 服务商申请及审核，不是商品销售身份 |
| Brand Registry 品牌注册 | 品牌相关资格体系 | 品牌后台及关联角色 |
| SP-API Role 应用角色 | 软件可访问哪些业务资源 | 开发者资料、应用配置及重新授权情况 |

- 使用 FBA 不会把 Seller 变为 Vendor；公司可能同时有卖家与供应商业务，确认其中一个账户类型不能排除另有另一类账户。
- **品牌分析可读不能证明操作人是品牌所有者或管理员。**
- 角色不是唯一身份标签，一个应用可以拥有多项权限。
- **读取报表列表返回 200，不足以证明可以生成任意报表**；列表为空既不能证明没权限，也不能证明没有业务。
- 新增角色可能需要开发者审核、更新应用并重新授权。

参考：[SP-API 角色定义](https://developer-docs.amazon/sp-api/docs/roles-in-the-selling-partner-api) · [接口角色权限对照表](https://developer-docs.amazon/sp-api/lang-zh_CN/docs/role-mappings) · [Seller Central 与 Vendor Central 区别](https://sell.amazon.com/tools/seller-central)

| 实践 | 覆盖公共网络、跨网络边界与第三方交互；非可信环境端到端加密；独立数据库或来源标签；自动化删除 |

**【解读】** 把敏感数据接进 ERP 后，还要知道数据在哪里、谁能看、什么时候应删除。照片中的"30 天"不是对所有经营数据统一保留 30 天的结论，也不能脱离完整政策解释例外。

### 6.2 漏洞扫描与渗透测试【现场 IMG_2396】

- 至少每 **30 天**开展一次全量扫描
- 重大变更后立即重新扫描
- 每次软件发布前执行代码扫描
- 每 **365 天**开展一次全面渗透测试
- 严重漏洞 **7 天**内闭环，高风险漏洞 **30 天**内闭环
- 覆盖网络、云端、应用、API 和存储；采用认可的方法，集成自动扫描，保存扫描与修复记录

**漏洞扫描**是查找潜在弱点；**渗透测试**是在约定范围内模拟攻击，验证弱点能否被实际利用。照片没有给出风险分级标准与计时起点，需补正式规则后再制作企业执行表。

### 7.3 Data Kiosk 工作流的完整过程【实测 B】

1. 明确站点、完整日期、聚合维度和目标字段
2. 创建查询，等待后获取处理状态，设置有限轮询与失败分支
3. 确认查询完成及结果文档存在，获取下载地址
4. 下载 JSONL，检查文件存在并可解析
5. 到卖家中心按同站点、同日期和同筛选条件核对

**耗时说明：** 原记录为约 33 秒、1 条日汇总结果。该耗时包含本次流程的等待设置，**只是一次运行观察，不是效率提升比例或性能保证**。

**核对字段：** `orderedProductSales`（销售额）、`unitsOrdered`（订购件数）、`totalOrderItems`（订单商品项数）。最后一项**不是去重订单数**，实际经营数值不公开。

**遇到的问题与处理：** 过程中曾遇到网络连接重置、查询列表为空，以及最初后台站点或日期不一致。恢复连接、创建查询并统一筛选口径后，下载及三项对账成功。

> 空列表不能解释为店铺没有销售；导入成功也不能解释为流程一定可执行。

### 7.4 余额差异的排查结论【实测 C】

**排查过程：** 先核对站点、币种与账户类别，再检查 `lastUpdatedTime` 和本地请求路径，并绕过 MCP 向官方区域端点直接发起两次只读查询。

**观察结果：** 两次直连均返回 HTTP 200；请求标识不同、HTTP Date 变化、X-Cache 显示 Miss from cloudfront，但余额和 `lastUpdatedTime` 未变。已检查的 MCP 业务路径没有发现余额缓存，工具展示也未完整保留原始响应头。

**可以确认：** 旧余额不只出现在 MCP 中，直连也能复现，**不能把问题简单归咎于 MCP 独有缓存**。

**尚不能确认：** 亚马逊内部是否还有其他缓存、准确刷新周期、页面差额对应哪些交易，或差异是否涉及其他业务口径。此批没有完成后台与接口的逐笔对账。

**方法沉淀：** 记录请求时间、HTTP Date、业务数据的 `lastUpdatedTime`，可以区分"刚发出的请求"和"返回的是何时更新的数据"。数据更新时间由服务端返回；**重复调用不等于强制刷新**。

尚未完成公共应用网站回调、跨卖家数据隔离、全部接口和站点、长期稳定性、大数据量与异常分支的完整验证。促销写入、广告鉴权、BHDR 开放范围、MCF 预发布版本关系、余额差异逐笔归因，仍需要后续证据。

## 8 运营落地

### 8.1 把数据对应到五个业务问题

| 问题 | 主要数据 | 还要补什么 |
|---|---|---|
| 店铺有没有风险 | 商品问题、订单与履约异常 | 账户绩效、政策通知、工单和退货详情 |
| 卖得怎么样 | 订单、销量、销售额、流量（会话、浏览） | 完整日期、订单状态、前日与上周同日基线、退款口径 |
| 赚不赚钱 | 交易、费用、退款、净销售 | 采购、头程、包装、汇率、税务及外部成本分摊 |
| 广告有没有浪费 | Ads API 花费与归因销售，结合整体销售 | 商品利润、归因窗口、投放目的与搜索词 |
| 库存是否安全 | 可配送、预留、不可售及在途库存 | 销量、补货周期和到货可靠性 |

> 本汇编没有读取任何店铺数据，因此没有得出"广告浪费""断货"或"利润下降"等店铺诊断结论。

### 8.2 三个优先场景

| 场景 | 最小可行输出 | 验证办法 |
|---|---|---|
| 销售日报 | 单站点、完整日期的销售与销量汇总 | 与后台同口径核对，记录更新时间 |
| 商品搜索诊断 | 曝光到购买各环节的异常商品及待查原因 | 用完整可比周期，一次验证一个主要变量 |
| 促销利润复盘 | 活动销售、折扣、费用、广告及成本的对应关系 | 比较可比基线或对照，避免把全部活动销售当增量 |

库存与订单巡检可在上述流程上继续接入，但应分别验证权限、分页与字段含义。**高 ACoS、余额减少或单日销量下降，都不足以单独决定关广告、判断冻结或大量补货。**

### 8.3 统一分析表的拼表顺序

1. 先固定账号、商城、币种、站点时区、完整日期与数据更新时间。
2. 商品级表按**账号＋商城＋日期＋子 ASIN** 汇总；若用 SKU，先确认 SKU 与 ASIN 映射是否一对一。
3. 广告活动／广告组先聚合到同一商品日期粒度，再关联整体销售；否则多个活动会把同一商品的总销售额**重复计算**。
4. 保留稳定的活动和广告组 ID，名称主要用于展示。
5. 同时保存广告归因窗口和字段定义，区分订单数、销量件数、订购销售额、净销售额与广告归因销售额。
6. 检查缺失、重复、分母为零与广告归因回补，再计算比率；**不能把空值一律当零**。

### 8.4 一个流程的验收顺序

先确认目标和权限 → 对齐数据口径 → 校验流程定义 → 运行小范围查询 → 确认文件可用、结果与后台一致 → 记录失败情况。

提交查询不要盲目重复重试，已有查询应支持继续处理。长期运行还需要调度器、持续可用的运行环境、限流控制、失败恢复、日志和人工处理。**单次成功不等于每日自动运行；AI 生成迁移建议也不等于代码已经编译测试通过。**

### 8.5 三个学习卡（新人可直接照做）

#### 卡 A：企业购标签核对

- **场景：** 企业客户反馈包裹难以对应采购单
- **步骤：** 确认企业购订单 → 核对 PO 字段 → 核对收货公司 → 比对 ERP 展示 → 比对承运人标签
- **判断标准：** 原始订单、ERP、标签上的关键内容一致；缺失项明确提示；字段太长不会悄悄截断
- **常见错误：** 只有公司名称没有 PO；订单已更新但标签仍用旧缓存；把现场示例当成所有承运人通用字段

#### 卡 B：促销巡检

- **场景：** 活动建好了，但部分商品没有出现预期优惠
- **步骤：** 搜索活动 → 看完整活动状态 → 查询全部商品选择页 → 找到商品级问题 → 回后台核对商品资格与买家端展示
- **判断标准：** 活动 ID、站点、起止时间、商品范围、优惠条件一致；能解释是活动层还是商品层问题
- **常见错误：** 只查第一页；把活动正常当成所有商品正常；把满减直接扣到每件商品上；把能查询误认为能修改

#### 卡 C：整体销售与广告拼表

- **场景：** 想判断销量变化与广告投入是否有关
- **步骤：** 定账号／站点／完整日期／币种 → 定子 ASIN 或 SKU 粒度 → 先汇总广告 → 关联整体销售 → 查重复与缺失 → 计算指标 → 写证据与待验证原因
- **判断标准：** 关联前后整体销售总额不被放大；各字段单位清楚；广告窗口和数据更新时间可见；分母为零不输出误导比例
- **常见错误：** 把 `sales7d` 当作全部销售；订单数当件数；把所有活动行上的整体销售加总；当天未完整数据与完整日直接比较

### 8.6 三道判断题

**题 1｜自然销量能不能直接相减？** 某天总销量 100 件，广告报表 `orders7d` 为 30，能否得出自然销量 70 件？

> **不能。** 总销量是件数，`orders7d` 是订单数，而且日期、归因窗口、商品归属仍可能不同。先找同口径的广告件数字段并确认归因逻辑；无法对齐时，不输出精确自然销量。

**题 2｜这件商品现在便宜了多少？** 某商品标价 14.79 美元，提示"选定商品满 30 美元减 5 美元"，能否记成成交价 9.79 美元？

> **不能。** 优惠有门槛和适用商品条件，还需确定订单如何满足条件、优惠如何分摊。记录原价、促销形式、门槛与适用范围，比强行写一个无条件折后价更准确。

**题 3｜AI 已经把迁移做完了吗？** AI 列出四个 Java 文件的 Critical 问题并给出修改方向，是否表示迁移完成？

> **不表示。** 照片证明的是分析过程。还需确认正式目标版本、实施修改、编译、测试订单创建／取消／追踪、处理失败和回滚。本次资料里正式演讲页与演示目标版本还不同。
