# 3 业务接口分主题

## 3.1 Orders 订单

### 新 GET 工作流【现场 IMG_2331】

- 操作名称：`SearchOrders`
- 路径：`/orders/2026-01-01/orders`
- 筛选维度：创建时间前后、最近更新时间前后、订单状态、商城 ID、履约渠道（FBM/FBA）、包含的数据集

标题强调"流程统一，一次调用获取全部信息"。**【解读】** 以前需要分开查询订单、买家、地址、包裹再拼接；新方向是按需获取更完整的订单对象。但"一次调用"是演示表达，不能理解成任意数量的订单都不用分页或补充查询。权限、分页和业务状态限制依然存在。

### 代码演示中的字段变化【现场 IMG_2333】

Python 演示注释为 "Orders API 2026-01-01"、"1 call per order | no RDT"，用 `included_data` 请求 `BUYER`、`RECIPIENT`、`PROCEEDS`、`PACKAGES`。

| 演示所列变化 | 对开发工作的含义 |
|---|---|
| `fulfillment_channels` → `fulfilled_by`，`MFN` → `MERCHANT` | 请求字段与枚举需重新映射 |
| `order_statuses` → `fulfillment_statuses`，`Unshipped` → `UNSHIPPED` | 状态拼写及大小写不可直接沿用 |
| 去掉 `payload` 外层 | 旧响应解析代码可能需要调整 |
| `amazon_order_id` → `order_id` | 订单标识字段的读取方式需核对 |
| `included_data` 按需获取多类信息 | 数据选择与应用权限需要一起检查 |
| PII 由应用角色限制，不再往返获取 RDT | "不需要 RDT"不表示任何应用都能获取敏感信息 |

> **同组照片存在表达差异【待核实 Q04】**
> IMG_2331 示例使用 `status=Unshipped`（幻灯片 URL 示例），IMG_2333 使用 `fulfillment_statuses=["UNSHIPPED"]`（Python 演示）。不要拼接成一段未经验证的可运行请求；最终参数按实际采用版本的接口定义核对。

**PII** 是可识别个人的信息；**RDT** 是 Restricted Data Token（受限数据令牌）。新 Orders 不要求额外 RDT，不代表所有 SP-API 都取消 RDT【待核实 Q05】。

### 对运营的实际影响【解读】

可向 ERP 团队提出的需求：订单同步能否同时带出企业购标识、PO、收货公司、金额与包裹；同步失败是否有提示；更新后的订单能否重复抓取而不重复建单。

验收时更应看"有没有漏单、重复单、缺地址或丢包裹"，而不只看接口是否返回成功。

参考：[Orders API v2026-01-01 发布公告](https://developer-docs.amazon/sp-api/changelog/new-introducing-the-orders-api-v2026-01-01) · [迁移指南](https://developer-docs.amazon/sp-api/docs/orders-api-migration-guide)

## 3.2 Listings 商品

**Listing** 是卖家在某站点的商品刊登信息；**Marketplace** 是具体销售市场；**ASIN** 是亚马逊商品标识；**SKU** 是卖家管理编码。

### 同一区域多商城检索【现场 IMG_2349】

`getListingsItem` 与 `searchListingsItems`：

1. 可接受**同一区域**的多个商城 ID，一个请求检索多个商城的商品信息。
2. 响应可包括概要、报价、属性与问题；各项带商城 ID，便于识别来源。
3. 可减少对同一商品逐站点连续调用。
4. 对单商城请求保持向后兼容。
5. **仅适用于卖家**；投影片说明供应商代码映射至单一商城。
6. `searchListingsItems` 的筛选与排序（如 `withStatus`、`sortBy`）按第一个 ID（主商城）评估。

> **容易踩的坑：** 返回多个站点的数据，不等于每个站点都独立执行了一次相同筛选；第一个商城 ID 的选择会影响查询结果。也不能把"同一区域"扩展为任意跨区域组合。报表中必须保留站点维度。

### 运营场景【解读】

适合建立同一 SKU 在多个站点的属性、报价与问题清单。报表至少保留"卖家／账号、站点、SKU、ASIN、问题类型、抓取时间"，避免不同站点覆盖彼此。

议程主题是"首次提交即成功上架 ASIN"，但本批没有完整的商品类型要求、提交前校验、问题修复与发布结果页，**因此不重建一套声称来自现场的完整上架 SOP**【待核实 Q18】。

资源照片 IMG_2352 展示 `linktr.ee/amzn_listing`，另有"管理商品信息问题""管理可售商品"两个二维码，链接内容尚未访问。

## 3.3 Promotions 促销

### 能力地图【现场 IMG_2363】

四类：卖家／供应商级数据、促销状态、筛选条件、多种促销类型。

- 可同步促销当前状态
- 按促销类型、ASIN、日期范围、修订版类型筛选
- 促销类型包括优惠、优惠券、价格折扣、购物篮构建

"购物篮构建"可理解为鼓励买家凑单或满足组合购买条件，例如满一定金额减免。准确资格仍要看活动条件。

### 三个读取操作【现场 IMG_2364】

| 操作 | 现场说明 | 可以回答的问题 |
|---|---|---|
| `searchPromotions` | 按条件搜索，分页返回摘要：标题、预算、起止日期、状态、优惠力度、促销 ID、商城 | 有哪些活动，处于什么状态？ |
| `getPromotion` | 获取指定促销 ID 的完整数据及促销验证问题 | 某个活动为什么可能有问题？ |
| `getProductSelection` | 分页返回商品选择详情、专属优惠、商品级验证问题，支持超过 100 件商品 | 活动里哪些商品参与，哪些有问题？ |

> **应用建议【解读】：** 活动级"正常"不代表每件商品都无问题；运营看板要能从活动摘要下钻到商品选择。超过 100 件商品的场景尤其应检查分页是否全部读取。

**写入能力边界：** 创建更新在会场被列为未来计划（私测 2026 年底、正式 2027 年初），本批没有完成写入测试。**不能从读取可用推导出当前可以批量修改活动**【待核实 Q06、Q07】。

参考：[Promotions API](https://developer-docs.amazon/sp-api/docs/promotions-api)

## 3.4 Pricing 定价：竞争摘要与 FOEP

### getCompetitiveSummary 新增两个数据点【现场 IMG_2368】

**Similar Items（相似商品）** 与 **Promotions（促销）**。

**优惠券示例（IMG_2369）：** 商品展示价 99.99 美元，45% 优惠券；字段 `percentageOff: 45.0`、`type: PERCENTAGE_OFF`、折后价 `54.99 USD`、`promotionType: COUPON`。

**购物篮示例（IMG_2371）：** 标价 14.79 美元，符合条件的商品购买满 30 美元减 5 美元；字段 `promotionType: BASKET_BUILDING`、`AMOUNT_OFF`、`amountOff` 为 5 USD、购买门槛 `AT_LEAST` 为 30 USD。

> **判断标准：** 分析价格竞争力时需同时看优惠形式和满足条件。满 30 减 5 不能直接理解为每件商品减 5；优惠券也不能假设所有买家都已领取、适用或与其他活动叠加。金额仅为会议示例，不是当下商品报价。

### FOEP 推荐报价预期价格【现场 IMG_2372–2373】

**FOEP（Featured Offer Expected Price）** 用于评估争取 Featured Offer（推荐报价，运营常称购物车）时的价格参考。**没有承诺按该价格设置就一定获得购物车。**

- 操作：`getFeaturedOfferExpectedPriceBatch`
- 路径：`/batches/products/pricing/2022-05-01/offer/featuredOfferExpectedPrice`
- 每个请求最多 40 个 SKU
- 输入：商城编号、SKU、位置（可选）
- 返回示例含 `featuredOfferExpectedPrice`、`competingFeaturedOffer`、`currentFeaturedOffer`；示例状态 `VALID_FOEP`

| 用例 | 现场描述的方向 | 业务检查【解读】 |
|---|---|---|
| 自动调价 | 将价格设为等于或低于 FOEP，提高获得推荐报价的概率 | 要同时检查可接受利润与最低售价 |
| 价格竞争分析 | 了解目录中商品获得推荐资格的价格限额 | 注意站点、配送条件和查询时点 |
| 商品组合优化 | 按 FOEP 差值确定优先重新定价的 ASIN | 差值大不一定值得降价，还要看需求与利润 |
| 定价提醒 | 重要商品的 FOEP 大幅变化时通知卖家 | 先确认变化持续性，再决定动作 |

满额优惠不能逐件直接扣减，按参考价格调价也不保证取得购物车。

## 3.5 FBM 与 Easy Ship

**FBM（Fulfilled by Merchant）** 由卖家安排履约；**FBA（Fulfillment by Amazon）** 由亚马逊仓储配送体系履约。Easy Ship 的开通站点、仓库与资格未从照片确认。

### 外部配送 API 工作流【现场 IMG_2355】

| 顺序 | 业务动作 | 投影片操作名称 |
|---|---|---|
| 1 | 识别 Easy Ship 订单 | `getShipment` |
| 2 | 确认／拒绝订单 | `processShipment` |
| 3 | 分享包裹详情 | `createPackage` |
| 4 | 预约上门取件或线下送交 | `retrievePickupSlot` |
| 5 | 生成发票与标签 | `generateShipLabel`、`generateInvoice` |

> **边界：** 照片没有每个操作的完整请求或预约确认步骤。`retrievePickupSlot` 名称体现"获取取件时段"，**不能断言一次调用就已完成预约**。

## 3.6 MCF 多渠道配送

**MCF（Multi-Channel Fulfillment）** 指用亚马逊配送能力承接不同销售渠道的订单。照片未覆盖各地区资费、库存资格和渠道限制。**MCF 面向多渠道订单履约，不能与普通站内 FBA 买家订单混为一套业务。**

### 出库 API 功能清单【现场 IMG_2380 / IMG_2387】

- 预览与服务报价：`getOrderPreview`、`getOffers`
- 订单操作：`createOrder`、`getOrder`、`updateOrder`、`cancelOrder`
- 沙盒操作：`updateOrderStatus`、`UpdatePackage`（投影片大小写如此）
- 增值服务、通知 API、上传数据 API、追踪 API

**沙盒**是用于模拟测试的环境，例如模拟包裹延误，验证软件会不会发出正确提醒。

### v2026-07-04 新功能【现场 IMG_2388】

1. `updatePackage` 沙盒操作支持含多批货件的订单，以及已配送、延迟、在途等细化状态模拟
2. 通过配送服务进行基于渠道的配置，并使用默认设置
3. 与新版通知 API 数据结构保持一致，包含货件／包裹级事件和更丰富的订单商品内容
4. 支持 Webhook 订阅与 SQS
5. 支持商品级定制，如装箱单
6. 新的 `getShipmentTracking` 支持投影片所说的"免授权访问"

**Webhook** 即"发生变化时主动通知你的系统"；**SQS** 是消息队列服务。"免授权"在照片中没有完整认证上下文，**不能解释成不需要任何身份验证、密钥或访问控制**【待核实 Q10】。

### 追踪与通知的两条路线【现场 IMG_2389】

| 方式 | 操作或事件 | 内容 |
|---|---|---|
| 通知（投影片推荐） | `FULFILLMENT_ORDER_STATUS` | 接收订单、货件和包裹物流追踪更新 |
| 按追踪编码订阅 | `SHIPMENT_TRACKING_MILESTONE_CHANGED`（图示"免授权"） | 接收详细包裹物流更新 |
| 主动拉取 | `listOrders`，`updatedAfter >= 上次检查时间` | 获取有更新的订单 |
| 主动拉取 | `getOrder` | 查看订单、货件和包裹状态 |
| 主动拉取 | `getShipmentTracking`（图示"免授权"） | 查询物流追踪 |

**【解读】** 若开发通知系统，需考虑重复事件、乱序事件和漏消息后的补查。这是实现可靠提醒时的验证项目，不是照片展示的完整架构。

### 开发者门户【现场 IMG_2394】

面向构建 MCF 集成的自助门户，资源包括 API 参考文档、动态沙盒指南、MCF 用例指南、代码示例集。二维码原图已归档，目的地址尚未确认【待核实 Q16】。

## 3.7 Amazon Business 企业购

### 从 B2C 运营走向企业采购运营【现场 IMG_2322】

**B2C** 卖给个人消费者，**B2B** 卖给企业或机构，**AB（Amazon Business）** 指亚马逊企业购。投影片提出的困难是：2C 和 2B 放在一起运营，难以针对企业买家提升选品、流量与曝光。

| 现场列出的环节 | 代表工具或能力 |
|---|---|
| 选品与便利 | 商机探测器、选品指南针、品牌分析、A+ 与高级 A+ |
| 流量与转化 | 买家评论计划、优惠券组合拳、旺季活动、展示型推广、商品推广、品牌推广 |
| 多件订单 | 买一送一、订阅并保存 |
| 价格竞争力 | 自动定价、价格折扣、多买多省 |
| 物流配送 | 供应链智能托管、全球物流、跨境承运伙伴方案、入仓分销网络、多渠道分拨、亚马逊物流、卖家自配送、新品入仓优惠计划 |
| 售后复盘 | 退货管理、冗余库存管理 |

这是会场展示的运营工具地图，不代表本次逐一发布这些工具。

### BHDR Performance API：计划中的能力【现场 IMG_2326】

标注"即将推出""将于 2026 年第三季度推出"，列出能力：以编程方式访问 BHDR 数据、生成自动化合规提醒、减少在卖家平台的手动监控、提供卖家实时控制面板、嵌入现有卖家绩效报告。

**状态判断：** 这是发布计划，不确认在整理日已开放。照片未解释 BHDR 全称、计算分母、阈值、支持站点与权限要求【待核实 Q03】。

### 打印 PO 编号与公司名称【现场 IMG_2327】

**PO（Purchase Order，采购订单）编号**：企业内部用于匹配采购、收货和付款的编号。现场列出的痛点：企业客户要及时核对包裹；缺失信息会打乱三方匹配流程；共用收货口难以盲分拣；人工核对拖慢付款；退货与缺陷风险增加。

| 步骤 | 实现方向 |
|---|---|
| 1. 识别 AB 订单 | 检查 Orders API 响应 `programs` 是否包含 `AMAZON_BUSINESS` |
| 2. 获取 PO 编号 | Orders API v2026，`includedData = BUYER`，读取 `buyer.buyerPurchaseOrderNumber` |
| 3. 获取公司名称 | 读取 `recipient.deliveryAddress.companyName` |
| 4. 打印到标签 | 映射到承运人参考字段，例如 FedEx `P_O_NUMBER`、UPS Reference |

脚注称通过"购买配送"购买的货件标签会自动打印 PO 编号和公司名称；具体覆盖条件需后续核实。

**【解读】验证方式：** 用一个获授权的企业购测试订单，逐项对照订单字段、ERP 展示和最终标签；检查长公司名称是否截断、PO 缺失时是否明确提示。

> 使用 FBA 不会把 Seller 变为 Vendor，企业客户使用 PO 也不会改变卖家身份。

## 3.8 Finances 财务

> 议程确认有一场"2026 财务 API：简化亚马逊卖家的财务数据与付款管理"，但**本批照片没有可明确归属该场的接口介绍、付款流程或版本说明**，因此不补写未拍到的内容【待核实 Q02】。本节内容来自官方文档与 C 批运营接口／对账记录。

### 财务接口七项清单【官方 + 实测】

以下为本次目录中的 Finances 七项操作，均为读取。**新旧接口可能覆盖相同业务事件，不可将两套数据简单相加。**

| v0 | listFinancialEventGroups | `/finances/v0/financialEventGroups` | 财务事件分组 |
| v0 | listFinancialEventsByGroupId | `/finances/v0/financialEventGroups/{eventGroupId}/financialEvents` | 组内明细 |

参考：[Finances 总览](https://developer-docs.amazon/sp-api/docs/finances-api) · [交易明细参考](https://developer-docs.amazon/sp-api/docs/finances-api-v2024-06-19-reference) · [listSummary](https://developer-docs.amazon/sp-api/reference/listsummary)

### 财务数据能辅助对账，不能单独算出完整净利润

采购、头程、包装、税务处理、汇率、站外成本及广告消耗分摊需要补齐。**订单净额不等于利润；费用优惠抵扣到零不等于费用永久取消。**

按首次记账分析经营收支与按释放日期分析现金流，是两种不同报表。出现 `DEFERRED_TRANSACTION_ID`、`RELEASE_TRANSACTION_ID` 等关联时，要核验原始交易与释放交易的关系，避免重复计收入；**也不能无条件删除所有释放记录**，因为原始交易可能在其他期间。

`listTransactions` 官方提示可能未包含最近 48 小时的订单财务记录。这是完整性与时效限制，**不能扩展为"所有财务接口都延迟 48 小时"或"48 小时内金额必然错误"**。分页要读到结束，空页也可能仍有下一页。

### 可用、暂缓和到账

余额可能包含 AVAILABLE（可用）、RESERVED（预留）及其下层 DEFERRED（暂缓）、ACCOUNT_LEVEL_RESERVE（账户级预留）。**核对层级后再求和，不能把父项与子项重复相加。**

暂缓的常见原因包括配送日期预留 DD7 以及企业买家账期 B2B。DD7 通常与送达后预留期有关，不是等待买家手动点击确认收货；企业账期则可能等待买家支付发票。**预计释放日期不是银行到账日期。**

资金通常经历"暂缓 → 释放 → 纳入结算付款 → 银行到账"。余额少不等于违规冻结。费用支付还取决于卖家扣款方式及广告账单设置；负余额不代表无限赊账，付款失败可能影响广告或账户使用。具体应核对到期账单、备用付款方式和后台通知，而不是仅凭余额判断。

参考：[暂缓交易说明](https://sellercentral-europe.amazon.com/seller-forums/discussions/t/3fe1fff3-f924-42bc-aa45-69244e8d6f83) · [广告付款方式说明](https://advertising.amazon.com/library/news/update-on-advertiser-payments) · [负余额处理说明](https://sellercentral.amazon.com/seller-forums/discussions/t/6e57e55b-9a25-4a8e-a6cd-e837040ec33f)

## 3.9 Reports 分析报表

### 四种值得了解的报表【官方】

| reportType | 业务用途 | 权限与口径重点 |
|---|---|---|
| `GET_BRAND_ANALYTICS_SEARCH_QUERY_PERFORMANCE_REPORT` | 搜索词与商品的曝光、点击、加购、购买份额 | Brand Analytics 及品牌注册资格；**必填** `reportOptions.asin` |
| `GET_BRAND_ANALYTICS_SEARCH_CATALOG_PERFORMANCE_REPORT` | 商品在搜索过程中的转化表现 | Brand Analytics 及品牌注册资格；**可选** `reportOptions.asins` |
| `GET_COUPON_PERFORMANCE_REPORT` | 领券、用券、折扣、预算和销售表现 | 卖家 Brand Analytics 角色 |
| `GET_PROMOTION_PERFORMANCE_REPORT` | 促销浏览、销量和销售表现 | 卖家 Selling Partner Insights 角色；供应商要求另核对 |

**口径要点：**

- 搜索查询报表必填 `reportOptions.asin`；商品搜索报表可选 `reportOptions.asins`，**两者不要混写**。
- 前两类支持周、月、季度；按周使用**周日至周六**，单次不跨多个周期。
- 搜索表现不能直接当广告效果或全店流量。
- 优惠券和促销按**活动开始日期**筛选，可能返回跨月活动累计表现，**并非按筛选月份切片**；两类每日更新。
- 卖家促销效果报表当前列出的覆盖为 Best Deal、Lightning Deal，不应假定全部优惠形式都包含。

### 通用调用链

| 操作 | HTTP 与路径 | 说明 |
|---|---|---|
| getReports | `GET /reports/2021-06-30/reports` | 查已有报表 |
| createReport | `POST /reports/2021-06-30/reports` | 生成报表任务，**不是创建促销** |
| getReport | `GET /reports/2021-06-30/reports/{reportId}` | 查状态及文档标识 |
| getReportDocument | `GET /reports/2021-06-30/documents/{reportDocumentId}` | 取下载信息，再下载并按需解压 |

`createReport` 虽使用 POST，用途是生成分析任务；反过来也不能把所有 POST 都当成无业务影响的查询。

参考：[品牌分析报表及参数](https://developer-docs.amazon/sp-api/docs/report-type-values-analytics) · [促销及优惠券报表](https://developer-docs.amazon/sp-api/docs/report-type-values-performance)

## 3.10 Data Kiosk 与 Ads API 数据分析

### Data Kiosk 查询构建【现场 IMG_2405–2406】

**Data Kiosk** 用于按数据结构构建查询。**Schema** 告诉开发者有哪些字段、参数和数据类型；**GraphQL** 是按所需字段描述查询的一种方式。

- 数据结构：`analytics_salesAndTraffic_2024_04_24`
- 查询：`salesAndTrafficByAsin`
- 聚合维度：`aggregateBy: CHILD`（按子 ASIN）
- 参数：`startDate`、`endDate`、`marketplaceIds`
- 可选字段示例：`childAsin`、`orderedProductSales`、`orderedProductSalesB2B`、移动端浏览与会话相关字段

> **可确认的是查询构建过程，照片未显示一次成功执行后的真实结果。** 日期和商城输入在画面中是空值或占位内容，不能照抄为生产查询。结构名称中的 2024-04-24 是版本标识，不是大会日期。

### 跨领域供应商指标地图【现场 IMG_2407】

供应商视角**不能**直接等同于普通第三方卖家账号都可读取的字段【待核实 Q14】。

| 领域 | 指标方向 |
|---|---|
| 选品 | ASIN、商品名称、款式编号、发布日期；IDQ 等级和分数、A+ 覆盖率；可购买报价、可购买 ASIN、转化率 |
| 买家体验 | 配送速度与 UFT、可快速追踪的有货商品；可售／不可售库存、售罄率；促销 OPS、SnS 收入渗透率；订购／发货收入；退货与评分 |
| 流量 | 搜索词关键词得分、排名、ASIN 占比；目录搜索展示次数、优惠徽章、点击率；广告、浏览量 |
| 卖家运营 | 供应商确认率、整体交付周期、信用卡拒付总金额；会计核算；合作推广费、已发货 COGS、销售折扣；第 1–26 周均值、P70、P90 预测；账户状态 |

IDQ、UFT、OPS、SnS 在照片中无完整定义，保留原缩写；COGS 通常指销售商品成本。**不能把预测分位数当成已发生销量**；供应商确认率、已发货 COGS 也不宜直接套到卖家利润分析。

### 卖家财务指标地图【现场 IMG_2408】

| 组别 | 可见字段内容 |
|---|---|
| 广告与净收益 | 广告类型名称、广告费用及金额／每单位金额／促销金额／税费；净收益每单位与总额 |
| 成本 | 销货成本；亚马逊物流成本、发往亚马逊成本；卖家自配送的配送／仓储成本；杂项成本 |
| 费用 | 费用类型名称；汇总明细费用与组件明细费用；金额、每单位金额、促销金额、税费金额、总金额、数量 |
| 销售与关联标识 | 平均销售价格、商品净销售额、已订购／已退款商品销售额；净销售量、订购／退款数量；子 ASIN、父 ASIN、MSKU、FNSKU、商城编号 |

**"卖了多少"与"赚了多少"需要不同字段。** 照片列出了框架，但没有展示采购成本、头程、汇率是否已录入，不能据此认为系统天然掌握完整利润。该页也**不能替代财务 API 专场的会议记录**。

### Amazon Marketing Stream【现场 IMG_2410】

三个优势：**统一**（数据一致性有助于减少并行集成和整合成本）、**可定制**（订阅控制可配置数据交付方式、频率和粒度）、**可扩展**（较快获取近实时数据，支持持续、高频使用场景）。

**【解读】** 可把"定时去索取数据"转为"订阅后接收数据变化"的一部分工作。投影片没有承诺所有指标都即时最终定稿，也没有列明每个数据集的延迟和修订机制。

### 构建统一分析表：两个数据域要先对齐【现场 IMG_2411–2412】

| 数据域 | 现场列出的字段 | 业务含义 |
|---|---|---|
| SP-API 商品标识 | `childAsin`、`parentAsin`、`sku`、`marketplaceId` | 哪个商品、哪个站点 |
| SP-API 销售 | `orderedProductSales`、`netProductSales`、`averageSellingPrice` | 整体订购、净销售与平均售价 |
| SP-API 流量 | `sessions`、`pageViews`、`buyBoxPercentage` | 会话、浏览、购物车占比 |
| Ads API 标识 | `advertisedAsin`、`advertisedSku`、`campaignName`、`adGroupName` | 广告推广的商品与投放路径 |
| Ads API 表现 | `impressions`、`clicks`、`cost`、`sales7d`、`orders7d` | 展示、点击、花费及 7 天归因销售与订单 |

补充照片 `B02-01_统一分析表.jpg` 是同一页更完整的一张，左侧字段清单与右侧统一输出框在同一画面内，可用于核对上表字段是否抄全。IMG_2412 的统一输出写了：自然销量 = 总销量 − 广告销量；TACoS = 广告支出 ÷ 总销售额；从展示到点击、从会话到购买贯穿付费与自然渠道。

> **会议中的简化公式，需要口径校验后才能用于真实店铺【待核实 Q15】**
> `orders7d` 是订单指标，不能直接当作销量件数；`sales7d` 是广告归因销售额，不能直接与任意净销售额相减。订单日期与广告归因日期、退款处理、币种、站点、归因窗口及跨商品归因都可能不同。未对齐前，"总量减广告量"最多保留为**待验证差额**，不能命名为准确的自然销量，也不能据此证明广告带来的增量。

**ACoS 的分母是广告归因销售额，TACoS 的分母是整体销售额。** 订单数、件数、订购销售额、净销售额和投放日／归因日不能混算。

SP-API 授权成功不等于广告授权成功。欧洲 SP-API 与 Ads API 地址分别是 `sellingpartnerapi-eu.amazon.com` 和 `advertising-api-eu.amazon.com`；后者的账户列表请求还需要广告鉴权。
