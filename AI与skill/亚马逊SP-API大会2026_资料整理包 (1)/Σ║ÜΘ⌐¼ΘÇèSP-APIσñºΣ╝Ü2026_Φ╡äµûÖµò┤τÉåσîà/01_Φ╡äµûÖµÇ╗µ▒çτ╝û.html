1.3 三条主线

  1. 接口把订单、商品、履约和经营数据连接起来。
  2. AI 与 MCP 帮开发者理解、调用和迁移接口。
  3. 运营分析需要把店铺整体表现与广告表现放在一起看。

对运营新人，最有价值的不是背接口名称，而是知道 ERP 能解决哪些问题、数据是否完整，以及可以向技术人员提出什么具体需求。

1.4 最需要保留的四个判断

  1. 读取能力与写入能力分开看。 促销读取已发布的现场口径，不等于创建更新也已开放。
  2. AI 输出要回到版本与测试。 迁移演示有明确的预发布提示，与另一页版本不同，不能直接上线照用。
  3. 数据连接要先统一口径。 站点、时间、币种、粒度和归因窗口对不上，漂亮的统一看板也可能误导运营。
  4. API 接入包含持续维护。 同步、分页、错误处理、权限、删除与测试，都是软件可用性的一部分。

1.5 核心结论

现有测试记录已覆盖官方 MCP 安装与库存读取、部分订单与财务查询，以及一次 Data Kiosk 销售汇总工作流和后台对账。它们证明了具体链路可以跑通；完整利润、广告优化和长期自动化仍需要更多数据、权限与运行保障。

3 业务接口分主题

3.1 Orders 订单

新 GET 工作流现场 IMG_2331

  • 操作名称：SearchOrders
  • 路径：/orders/2026-01-01/orders
  • 筛选维度：创建时间前后、最近更新时间前后、订单状态、商城 ID、履约渠道（FBM/FBA）、包含的数据集

标题强调"流程统一，一次调用获取全部信息"。解读 以前需要分开查询订单、买家、地址、包裹再拼接；新方向是按需获取更完整的订单对象。但"一次调用"是演示表达，不能理解成任意数量的订单都不用分页或补充查询。权限、分页和业务状态限制依然存在。

代码演示中的字段变化现场 IMG_2333

Python 演示注释为 "Orders API 2026-01-01"、"1 call per order | no RDT"，用 included_data 请求 BUYER、RECIPIENT、PROCEEDS、PACKAGES。

演示所列变化 对开发工作的含义
fulfillment_channels → fulfilled_by，MFN → MERCHANT 请求字段与枚举需重新映射
order_statuses → fulfillment_statuses，Unshipped → UNSHIPPED 状态拼写及大小写不可直接沿用
去掉 payload 外层 旧响应解析代码可能需要调整
amazon_order_id → order_id 订单标识字段的读取方式需核对
included_data 按需获取多类信息 数据选择与应用权限需要一起检查
PII 由应用角色限制，不再往返获取 RDT "不需要 RDT"不表示任何应用都能获取敏感信息

同组照片存在表达差异待核实 Q04 IMG_2331 示例使用 status=Unshipped（幻灯片 URL 示例），IMG_2333 使用 fulfillment_statuses=["UNSHIPPED"]（Python 演示）。不要拼接成一段未经验证的可运行请求；最终参数按实际采用版本的接口定义核对。

PII 是可识别个人的信息；RDT 是 Restricted Data Token（受限数据令牌）。新 Orders 不要求额外 RDT，不代表所有 SP-API 都取消 RDT待核实 Q05。

对运营的实际影响解读

可向 ERP 团队提出的需求：订单同步能否同时带出企业购标识、PO、收货公司、金额与包裹；同步失败是否有提示；更新后的订单能否重复抓取而不重复建单。

验收时更应看"有没有漏单、重复单、缺地址或丢包裹"，而不只看接口是否返回成功。

3.2 Listings 商品

Listing 是卖家在某站点的商品刊登信息；Marketplace 是具体销售市场；ASIN 是亚马逊商品标识；SKU 是卖家管理编码。

同一区域多商城检索现场 IMG_2349

getListingsItem 与 searchListingsItems：

  1. 可接受同一区域的多个商城 ID，一个请求检索多个商城的商品信息。
  2. 响应可包括概要、报价、属性与问题；各项带商城 ID，便于识别来源。
  3. 可减少对同一商品逐站点连续调用。
  4. 对单商城请求保持向后兼容。
  5. 仅适用于卖家；投影片说明供应商代码映射至单一商城。
  6. searchListingsItems 的筛选与排序（如 withStatus、sortBy）按第一个 ID（主商城）评估。

容易踩的坑： 返回多个站点的数据，不等于每个站点都独立执行了一次相同筛选；第一个商城 ID 的选择会影响查询结果。也不能把"同一区域"扩展为任意跨区域组合。报表中必须保留站点维度。

运营场景解读

适合建立同一 SKU 在多个站点的属性、报价与问题清单。报表至少保留"卖家／账号、站点、SKU、ASIN、问题类型、抓取时间"，避免不同站点覆盖彼此。

议程主题是"首次提交即成功上架 ASIN"，但本批没有完整的商品类型要求、提交前校验、问题修复与发布结果页，因此不重建一套声称来自现场的完整上架 SOP待核实 Q18。

3.3 Promotions 促销

能力地图现场 IMG_2363

四类：卖家／供应商级数据、促销状态、筛选条件、多种促销类型。

  • 可同步促销当前状态

可用、暂缓和到账

余额可能包含 AVAILABLE（可用）、RESERVED（预留）及其下层 DEFERRED（暂缓）、ACCOUNT_LEVEL_RESERVE（账户级预留）。核对层级后再求和，不能把父项与子项重复相加。

暂缓的常见原因包括配送日期预留 DD7 以及企业买家账期 B2B。DD7 通常与送达后预留期有关，不是等待买家手动点击确认收货；企业账期则可能等待买家支付发票。预计释放日期不是银行到账日期。

资金通常经历"暂缓 → 释放 → 纳入结算付款 → 银行到账"。余额少不等于违规冻结。费用支付还取决于卖家扣款方式及广告账单设置；负余额不代表无限赊账，付款失败可能影响广告或账户使用。具体应核对到期账单、备用付款方式和后台通知，而不是仅凭余额判断。

4.3 工作流如何运行

链路： 业务目标 → AI 查接口与参数 → 创建或复用 JSON → 校验流程 → 本地执行器调用接口 → 保存结果与日志 → AI 解释结果。

JSON 用状态和转移规则描述步骤；ASL 是 Amazon States Language。本地工作流服务器使用 Node.js 执行器，提供等待、分支、文件获取、暂停恢复和人工输入等工具。某批连接记录发现 30 个工具，这只是该版本的观察值。

Data Kiosk 查询是异步的： 创建查询 → 等待完成 → 获取文档下载地址 → 下载 JSONL 文件。JSONL 每行是一条 JSON 数据，便于逐条解析。提交成功只表示任务已受理，不能代替完成状态和文件内容校验。

本地 JSON 与云端 JSON 不一定通用。 官方云端示例使用 AWS Step Functions 调度 Lambda；本地执行器支持的任务资源不同。测试中 AWS 示例原样导入成功，但运行时因不支持 Lambda 资源而失败，适配成本地任务后才跑通。

已有流程可查找、查看定义、导入、校验和执行。导出 Mermaid 流程图或独立 Node.js 脚本的能力通过工具及源码确认，但没有单独执行导出脚本。保存流程也不会自动创建每日定时任务。

5.4 自授权和公共应用授权

方式 适合场景 关键步骤
自授权 自己有资格授权的账号进行接入测试 在应用管理中授权，安全保存刷新令牌
公共应用 OAuth 让其他卖家接入自己的应用 注册登录与回调地址，验证 state，及时兑换授权码，按卖家隔离令牌和数据

公共应用可用自授权测试；但自授权成功不等于网站回调已通过验证。其他卖家不需要获得开发者的 Client Secret。回调网址背后必须有处理程序，仅填一个地址不构成完整授权服务。

刷新令牌是长期、可撤销的凭证；公共应用还涉及定期重新授权要求，不能承诺永久有效。自动换取 Access Token 也不等于可以自动恢复已撤销的卖家授权。

7.4 余额差异的排查结论实测 C

排查过程： 先核对站点、币种与账户类别，再检查 lastUpdatedTime 和本地请求路径，并绕过 MCP 向官方区域端点直接发起两次只读查询。

观察结果： 两次直连均返回 HTTP 200；请求标识不同、HTTP Date 变化、X-Cache 显示 Miss from cloudfront，但余额和 lastUpdatedTime 未变。已检查的 MCP 业务路径没有发现余额缓存，工具展示也未完整保留原始响应头。

可以确认： 旧余额不只出现在 MCP 中，直连也能复现，不能把问题简单归咎于 MCP 独有缓存。

尚不能确认： 亚马逊内部是否还有其他缓存、准确刷新周期、页面差额对应哪些交易，或差异是否涉及其他业务口径。此批没有完成后台与接口的逐笔对账。

方法沉淀： 记录请求时间、HTTP Date、业务数据的 lastUpdatedTime，可以区分"刚发出的请求"和"返回的是何时更新的数据"。数据更新时间由服务端返回；重复调用不等于强制刷新。

8.4 一个流程的验收顺序

先确认目标和权限 → 对齐数据口径 → 校验流程定义 → 运行小范围查询 → 确认文件可用、结果与后台一致 → 记录失败情况。

提交查询不要盲目重复重试，已有查询应支持继续处理。长期运行还需要调度器、持续可用的运行环境、限流控制、失败恢复、日志和人工处理。单次成功不等于每日自动运行；AI 生成迁移建议也不等于代码已经编译测试通过。

8.5 三个学习卡（新人可直接照做）

卡 A：企业购标签核对

  • 场景： 企业客户反馈包裹难以对应采购单
  • 步骤： 确认企业购订单 → 核对 PO 字段 → 核对收货公司 → 比对 ERP 展示 → 比对承运人标签
  • 判断标准： 原始订单、ERP、标签上的关键内容一致；缺失项明确提示；字段太长不会悄悄截断
  • 常见错误： 只有公司名称没有 PO；订单已更新但标签仍用旧缓存；把现场示例当成所有承运人通用字段

卡 B：促销巡检

  • 场景： 活动建好了，但部分商品没有出现预期优惠
  • 步骤： 搜索活动 → 看完整活动状态 → 查询全部商品选择页 → 找到商品级问题 → 回后台核对商品资格与买家端展示
  • 判断标准： 活动 ID、站点、起止时间、商品范围、优惠条件一致；能解释是活动层还是商品层问题
  • 常见错误： 只查第一页；把活动正常当成所有商品正常；把满减直接扣到每件商品上；把能查询误认为能修改

卡 C：整体销售与广告拼表

  • 场景： 想判断销量变化与广告投入是否有关
  • 步骤： 定账号／站点／完整日期／币种 → 定子 ASIN 或 SKU 粒度 → 先汇总广告 → 关联整体销售 → 查重复与缺失 → 计算指标 → 写证据与待验证原因
  • 判断标准： 关联前后整体销售总额不被放大；各字段单位清楚；广告窗口和数据更新时间可见；分母为零不输出误导比例
  • 常见错误： 把 sales7d 当作全部销售；订单数当件数；把所有活动行上的整体销售加总；当天未完整数据与完整日直接比较

8.6 三道判断题

题 1｜自然销量能不能直接相减？ 某天总销量 100 件，广告报表 orders7d 为 30，能否得出自然销量 70 件？

不能。 总销量是件数，orders7d 是订单数，而且日期、归因窗口、商品归属仍可能不同。先找同口径的广告件数字段并确认归因逻辑；无法对齐时，不输出精确自然销量。

题 2｜这件商品现在便宜了多少？ 某商品标价 14.79 美元，提示"选定商品满 30 美元减 5 美元"，能否记成成交价 9.79 美元？

不能。 优惠有门槛和适用商品条件，还需确定订单如何满足条件、优惠如何分摊。记录原价、促销形式、门槛与适用范围，比强行写一个无条件折后价更准确。

题 3｜AI 已经把迁移做完了吗？ AI 列出四个 Java 文件的 Critical 问题并给出修改方向，是否表示迁移完成？

不表示。 照片证明的是分析过程。还需确认正式目标版本、实施修改、编译、测试订单创建／取消／追踪、处理失败和回滚。本次资料里正式演讲页与演示目标版本还不同。
