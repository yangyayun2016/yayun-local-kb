# 天机 AI 智能体产品沟通文档

## 卖家精灵 MCP + 亚马逊运营 Skill 系统设计说明

## 1. 我们要做的不是“聊天机器人”，而是“亚马逊运营智能体系统”

用户在智能对话框里输入一个问题，例如：

> “@卖家精灵，帮我分析这个 ASIN 的流量来源和关键词机会。”
> “@卖家精灵，帮我反查 B0XXXXXXX 的出单词，看看广告怎么打。”
> “@卖家精灵，帮我判断 air purifier 这个细分类目还能不能做。”
> “@卖家精灵，帮我找一批低评论、高增长、有机会切入的产品。”

如果只是普通大模型，它可能会根据经验自由发挥，输出一堆看似合理但没有数据支撑的建议。

我们真正要做的是：

> 用户一句话输入需求 → 系统识别运营场景 → 调用卖家精灵 MCP 工具获取数据 → 进入我们预设的运营 Skill → 按固定方法论分析 → 输出结构化结果、评分、建议、下一步动作。

所以，天机 AI 智能体的核心不是“让 AI 随便回答”，而是：

1. 把亚马逊运营经验固化成 Skill；
2. 把卖家精灵 MCP 当作实时数据工具层；
3. 把大模型当作意图识别、任务拆解、分析组织和报告生成层；
4. 把最终结果变成可复用、可追踪、可迭代的运营决策系统。

---

# 2. 没有智能体时，运营平时会怎么做？

以一个成熟亚马逊运营的日常工作为例，如果没有智能体，通常流程是：

## 2.1 手动打开工具

运营会打开卖家精灵、亚马逊前台、广告后台、品牌分析、Google Trends、Keepa 等工具。

## 2.2 手动输入关键词或 ASIN

例如：

* 输入一个竞品 ASIN；
* 输入一个关键词；
* 输入一个类目；
* 输入多个竞品 ASIN；
* 输入一个品牌；
* 输入一个产品方向。

## 2.3 手动切换功能模块

比如在卖家精灵里反复切换：

* 查竞品；
* 查 ASIN 详情；
* 查关键词反查；
* 查出单词；
* 查流量来源；
* 查销量趋势；
* 查价格趋势；
* 查评论；
* 查市场规模；
* 查品牌集中度；
* 查 ABA；
* 查 Google 趋势。

## 2.4 手动下载、复制、整理数据

运营会把数据复制到 Excel、Notion、飞书、Obsidian 或内部表格中，自己做清洗、筛选、排序、对比。

## 2.5 根据经验做判断

例如：

* 这个产品是不是靠广告堆起来的？
* 这个关键词是不是有真实需求？
* 这个竞品是不是流量结构健康？
* 这个类目是不是被大品牌垄断？
* 这个市场有没有新品机会？
* 这个 ASIN 的出单词能不能拿来打广告？
* 这个 Listing 有哪些流量缺口？
* 这个产品的差评是否说明存在改良机会？

## 2.6 最后手动输出结论

最后可能输出：

* 一个竞品分析报告；
* 一个关键词表；
* 一个广告投放建议；
* 一个选品判断；
* 一个 Listing 优化方向；
* 一个产品改良方向；
* 一个市场进入评分；
* 一个老板能看懂的决策建议。

这个过程非常依赖人，而且耗时、不可标准化、难复制。

# 3. 有智能体后，应该变成什么样？

有天机 AI 智能体后，用户只需要输入自然语言：

> “帮我分析 B0XXXXXXX 的流量结构，看看这个竞品是不是靠广告打起来的。”

系统自动完成：

1. 识别场景：ASIN 流量诊断；
2. 识别实体：ASIN = B0XXXXXXX，站点 = US；
3. 自动调用 MCP 工具：

   * ASIN 详情；
   * 流量词反查；
   * 出单词反查；
   * 流量来源；
   * 销量趋势；
   * Keepa 历史趋势；
4. 进入“ASIN 流量诊断 Skill”；
5. 按固定逻辑分析：

   * 自然流量占比；
   * 广告流量依赖；
   * 关键词集中度；
   * 出单词数量；
   * 流量词与出单词重合度；
   * 价格、评分、评论、BSR 是否支撑转化；
6. 输出结构化报告：

   * 核心结论；
   * 数据摘要；
   * 风险判断；
   * 可复制打法；
   * 我方应对策略；
   * 下一步建议。

# 4. 系统核心原则：MCP 只是取数，Skill 才是运营大脑

卖家精灵 MCP 解决的是“数据怎么拿”的问题。

天机 AI Skill 解决的是：

* 拿哪些数据；
* 按什么顺序拿；
* 数据怎么组合；
* 指标怎么计算；
* 怎么判断好坏；
* 怎么输出结论；
* 怎么转化成运营动作。

所以技术架构上应该分成 4 层：

## 4.1 对话入口层

用户输入自然语言。

示例：

* “@卖家精灵，帮我查这个 ASIN 的核心流量词。”
* “@卖家精灵，分析 air purifier 这个市场。”
* “@卖家精灵，帮我找一批适合开发的产品。”
* “@卖家精灵，帮我反查竞品广告词。”
* “@卖家精灵，结合 Google 趋势判断这个关键词有没有站外热度。”

## 4.2 意图识别层

系统判断用户到底要做什么。

常见意图：

* ASIN 诊断；
* 竞品分析；
* 关键词反查；
* 出单词反查；
* 市场分析；
* 选品机会筛选；
* 广告架构建议；
* Listing 优化；
* Review 痛点分析；
* Google 趋势验证；
* ABA 趋势判断；
* 商标风险查询。

## 4.3 工具调用层：MCP Tools

系统根据意图自动选择卖家精灵 MCP 工具。

例如：

* 查 ASIN：`asin_detail`
* 查竞品：`competitor_lookup`
* 查销量趋势：`asin_sales_trend`
* 查销量预测：`asin_prediction`
* 查 BSR 预测销量：`bsr_prediction`
* 查流量词：`traffic_keyword`
* 查出单词：`keyword_order`
* 查流量来源：`traffic_source`
* 查关联流量：`traffic_listing`
* 查关键词拓展：`keyword_miner`
* 查 ABA：`aba_research_weekly`、`aba_research_monthly`
* 查 Google 趋势：`google_trend`
* 查市场：`market_research`
* 查评论：`review`
* 查商标：`trademark_list`、`trademark_detail`

## 4.4 Skill 分析层

这里是我们自己的核心竞争力。

Skill 不是简单 prompt，而是标准化运营流程。

每一个 Skill 都应该包含：

1. 使用场景；
2. 输入字段；
3. 必须调用的 MCP 工具；
4. 可选调用的 MCP 工具；
5. 数据清洗规则；
6. 指标计算规则；
7. 评分模型；
8. 判断逻辑；
9. 输出模板；
10. 异常处理；
11. 下一步动作建议。

# 5. 建议优先开发 8 个真实使用场景

## 场景 1：ASIN 竞品深度诊断 Skill

### 用户输入示例

> “@卖家精灵，帮我分析 B0XXXXXXX 这个竞品的优势和打法。”

### 没有智能体时，运营会做什么？

运营会手动查：

* ASIN 详情；
* 价格；
* BSR；
* 上架时间；
* 评论数量；
* 评分；
* 销量趋势；
* 销售额趋势；
* 优惠券；
* A+；
* 变体；
* 流量词；
* 出单词；
* Keepa 历史数据；
* Review 差评。

### 需要 MCP 工具

* `asin_detail`
* `competitor_lookup`
* `asin_sales_trend`
* `keepa_info`
* `traffic_keyword`
* `keyword_order`
* `review`
* `asin_coupon_trend`

### Skill 固定分析逻辑

系统需要固定判断：

1. 竞品基础实力：

   * 上架时间；
   * BSR；
   * 月销量；
   * 月销售额；
   * 评论数；
   * 评分；
   * 价格带；
   * 是否有 A+；
   * 是否有 Coupon。

2. 增长趋势：

   * 销量是否增长；
   * 销售额是否增长；
   * BSR 是否稳定；
   * 价格是否频繁波动；
   * Coupon 是否持续使用。

3. 流量结构：

   * 核心流量词数量；
   * Top 流量词集中度；
   * 自然流量强不强；
   * 广告流量依赖高不高。

4. 转化基础：

   * 评论数量是否支撑转化；
   * 评分是否有优势；
   * 价格是否有竞争力；
   * 差评是否集中在可改良问题。

5. 输出结论：

   * 竞品强在哪里；
   * 竞品弱在哪里；
   * 是否值得学习；
   * 我们能从哪里切入；
   * 广告、Listing、产品三个方向怎么打。

### 期望输出

* 竞品综合评分；
* 核心优势；
* 核心短板；
* 流量来源分析；
* 出单关键词；
* 可模仿打法；
* 可攻击点；
* 我方应对策略。

## 场景 2：关键词反查与关键词分层 Skill

### 用户输入示例

> “@卖家精灵，反查这个 ASIN 的关键词，帮我分成核心词、长尾词、场景词、属性词、广告词。”

### 没有智能体时，运营会做什么？

运营会进入卖家精灵关键词反查，导出流量词，然后手动分组：

* 大词；
* 精准词；
* 长尾词；
* 场景词；
* 人群词；
* 属性词；
* 功能词；
* 品牌词；
* 竞品词；
* 低相关词；
* 广告测试词。

### 需要 MCP 工具

* `traffic_keyword`
* `traffic_keyword_stat`
* `keyword_order`
* `keyword_miner`
* `traffic_extend`
* `aba_research_weekly`
* `aba_research_monthly`
* `aba_research_trend`

### Skill 固定分析逻辑

系统需要把关键词分成：

1. 核心大词
   搜索量高，竞争大，是类目主入口。

2. 精准成交词
   搜索意图明确，适合广告精准投放。

3. 长尾低竞争词
   搜索量较小，但转化可能更高。

4. 场景词
   例如 bedroom、office、car、pet、baby、travel。

5. 人群词
   例如 kids、women、men、pet owners、students。

6. 属性词
   例如 HEPA、cordless、portable、waterproof、stainless steel。

7. 痛点词
   例如 odor、allergy、stain、dust、noise。

8. 品牌词 / 竞品词
   用于判断竞品流量护城河。

9. 无效词 / 低相关词
   后续广告否词或排除。

### 期望输出

* 关键词分层表；
* 每类关键词数量；
* Top 关键词；
* 适合 Listing 的词；
* 适合广告精准的词；
* 适合广告广泛的词；
* 适合否词的词；
* 关键词机会评分。

## 场景 3：出单词反查与广告架构生成 Skill

### 用户输入示例

> “@卖家精灵，帮我反查这个竞品的出单词，然后生成我的广告架构。”

### 没有智能体时，运营会做什么？

运营会手动查竞品 Top 出单词，然后思考：

* 哪些词是真正成交词；
* 哪些词适合精准广告；
* 哪些词适合词组广告；
* 哪些词适合广泛广告；
* 哪些词适合低竞价捡漏；
* 哪些词适合 Listing 埋词；
* 哪些词不适合我们打。

### 需要 MCP 工具

* `keyword_order`
* `traffic_keyword`
* `keyword_miner`
* `aba_research_weekly`
* `traffic_source`
* `traffic_keyword_stat`

### Skill 固定分析逻辑

出单词不能直接照搬，需要判断：

1. 关键词相关性；
2. 关键词搜索量；
3. 关键词竞争强度；
4. 关键词是否被竞品垄断；
5. 关键词是否符合我方产品属性；
6. 关键词是否适合新品期；
7. 关键词是否适合成熟期；
8. 关键词是否可以做广告精准投放；
9. 关键词是否可以做低竞价捡漏；
10. 关键词是否应该加入 Listing。

### 广告架构输出

系统可以自动生成：

#### Campaign 1：核心精准词广告

* 目标：抢核心成交词；
* 匹配方式：Exact；
* 关键词来源：竞品 Top 出单词；
* 竞价策略：中高竞价；
* 预算优先级：高。

#### Campaign 2：长尾精准词广告

* 目标：拿低竞争成交词；
* 匹配方式：Exact / Phrase；
* 关键词来源：长尾出单词；
* 竞价策略：中低竞价；
* 预算优先级：中。

#### Campaign 3：词根拓展广告

* 目标：拓展新词；
* 匹配方式：Broad；
* 关键词来源：keyword_miner；
* 竞价策略：低竞价；
* 预算优先级：中低。

#### Campaign 4：竞品 ASIN 定投

* 目标：抢竞品详情页流量；
* 投放对象：竞品 ASIN；
* 筛选标准：价格更高、评分更低、评论更少、差评痛点明显的 ASIN；
* 预算优先级：中。

#### Campaign 5：低竞价捡漏广告

* 目标：低成本捕捉边缘流量；
* 关键词来源：低竞争长尾词；
* 竞价策略：低竞价；
* 预算优先级：低。

### 期望输出

* 出单词清单；
* 关键词投放分组；
* 广告 Campaign 架构；
* 广告匹配方式；
* 建议竞价区间；
* 预算优先级；
* 否词建议；
* Listing 埋词建议。

## 场景 4：市场进入机会判断 Skill

### 用户输入示例

> “@卖家精灵，帮我分析 air purifier 这个市场还能不能做。”

### 没有智能体时，运营会做什么？

运营会查：

* 市场容量；
* 销量规模；
* 销售额规模；
* 增长趋势；
* 品牌集中度；
* 商品集中度；
* 价格分布；
* 评论数分布；
* 评分分布；
* 新品占比；
* 上架时间分布；
* 卖家国家分布；
* 是否大牌垄断；
* 是否还有低评论新品机会。

### 需要 MCP 工具

* `market_research`
* `market_research_statistics`
* `market_product_concentration`
* `market_brand_concentration`
* `market_seller_concentration`
* `market_seller_country_distribution`
* `market_price_distribution`
* `market_ratings_count_distribution`
* `market_rating_distribution`
* `market_listing_date_distribution`
* `market_product_demand_trend`
* `market_ebc_distribution`

### Skill 固定分析逻辑

市场进入判断建议分 8 个维度：

1. 市场规模；
2. 市场增长；
3. 品牌集中度；
4. 商品集中度；
5. 价格带机会；
6. 评论壁垒；
7. 新品机会；
8. 差异化空间。

### 评分模型建议

总分 100 分：

* 市场容量：15 分；
* 增长趋势：15 分；
* 集中度：15 分；
* 评论壁垒：15 分；
* 价格带机会：10 分；
* 新品占比：10 分；
* 需求趋势：10 分；
* 差异化空间：10 分。

# 7. 技术开发需要理解的核心产品逻辑

## 7.1 大模型不能直接决定答案

大模型容易出现的问题：

* 没有数据也能编；
* 逻辑不稳定；
* 同一个问题多次回答不一致；
* 运营方法论不可控；
* 输出格式不可控；
* 不能沉淀公司经验。

所以要限制大模型：

> 大模型负责理解、拆解、组织语言；
> MCP 负责拿数据；
> Skill 负责判断逻辑；
> 系统负责格式化输出和留痕。

## 7.2 Skill 是系统里的“标准作业程序”

每个 Skill 相当于一个运营 SOP。

例如“ASIN 竞品分析 Skill”，它不是一句 prompt，而是一套流程：

1. 输入 ASIN；
2. 判断站点；
3. 调用 ASIN 详情；
4. 调用销量趋势；
5. 调用流量词；
6. 调用出单词；
7. 调用评论；
8. 做数据清洗；
9. 做指标计算；
10. 做评分；
11. 输出报告。

## 7.3 每个 Skill 都要可配置

建议 Skill 支持配置：

* 默认站点；
* 默认时间周期；
* 默认 Top N；
* 是否深度分析；
* 是否生成表格；
* 是否生成老板版摘要；
* 是否生成运营执行版；
* 是否生成广告架构；
* 是否生成 Listing 修改建议；
* 是否进入任务队列。

## 7.4 每次工具调用都要留痕

系统需要保存：

* 用户原始问题；
* 识别到的意图；
* 调用的 Skill；
* 调用的 MCP 工具；
* 输入参数；
* 返回数据摘要；
* 生成的结论；
* 用户是否采纳；
* 后续运营结果。

这样后面才能形成“天机自己的运营数据闭环”。

# 10. 给技术开发的关键需求总结

## 10.1 我们希望开发的不是一个“调用 MCP 的聊天框”

如果只是接入 MCP，用户仍然不知道怎么问、怎么分析、怎么判断。

我们要做的是：

> MCP + Skill + 运营方法论 + 结构化报告 + 数据闭环。

## 10.2 大模型回答必须受 Skill 约束

每个场景必须有固定流程，不能让大模型随便发挥。

例如：

用户说“分析这个 ASIN”，系统必须知道：

* 先查 ASIN 基础数据；
* 再查销量趋势；
* 再查流量词；
* 再查出单词；
* 再查 Review；
* 最后进入评分模型；
* 输出固定报告。

## 10.3 MCP 工具要统一封装

建议不要让前端直接调用 MCP。

而是后端封装成统一 Tool Service：

* 参数校验；
* 站点校验；
* 错误重试；
* 缓存；
* 日志；
* 额度控制；
* 返回数据标准化。

## 10.4 Skill 要支持后续扩展

未来我们会不断增加：

* 竞品分析 Skill；
* 关键词打标 Skill；
* 广告止损 Skill；
* Listing 打分 Skill；
* CDQ 质量评分 Skill；
* 新品推广计划 Skill；
* 坑位快照流量得分 Skill；
* 周围竞品出单概率 Skill；
* Review VOC Skill；
* 选品机会 Skill；
* Alexa / Rufus 问答优化 Skill。

所以开发时要把 Skill 做成可扩展架构。

# 11. 最终产品形态

天机 AI 智能体应该是一个“亚马逊运营专家工作台”。

用户输入：

> “帮我分析这个 ASIN。”

系统输出的不是普通聊天答案，而是一份运营可执行报告：

* 数据来自卖家精灵 MCP；
* 判断来自天机 Skill；
* 结构来自固定报告模板；
* 建议来自亚马逊运营经验；
* 结果可以沉淀到项目库；
* 后续可以继续生成广告架构、Listing 优化、选品判断和推广计划。

最终目标：

> 让普通运营也能按资深运营的思路做分析；
> 让资深运营的经验可以系统化复制；
> 让老板看到的是决策结果，而不是一堆原始数据；
> 让 AI 从“会聊天”变成“会做亚马逊运营动作”。
