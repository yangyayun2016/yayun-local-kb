01
TWO ERAS

Chat 时代 vs Agent 时代

💬

Chat 时代

交互方式：对话框输入提示词

AI 的角色：回答问题的助手

产出形式：文字回复，需要手动复制

质量取决于：你的提示词写得好不好

🤖

Agent 时代

交互方式：划定工作区，分配任务

AI 的角色：在工作区内独立工作的执行者

产出形式：直接修改文件、调用 API、输出文档

质量取决于：你给它的工作规范（Skill）写得好不好

Skill 就是你写给 Agent 的「工作手册」——不是一句话指令，而是一套完整的工作规范。

MECHANISM

Skill 的底层机制 — 渐进式加载

1

元数据层

~100 词
name + description
始终在上下文中
决定是否触发

2

指令层

<500 行
SKILL.md 主体
触发后加载
定义工作流程

3

资源层

无限
references/ scripts/ assets/
按需加载
不占常驻内存

渐进式加载 = 用最小的上下文成本，换最大的能力扩展。元数据像目录，指令像手册，资源像工具箱。

PART 02 / 01

AI 时代下的电商 SOP

  • 传统 SOP 的问题：写了没人看，看了记不住，记住了执行走样
  • Skill = 可执行的 SOP：不是给人读的文档，是给 AI 执行的程序
  • 一次编写，反复执行：同一套方法论，每次产出质量一致
  • 持续进化：用的过程中不断优化，越用越好

过去：SOP 写在文档里，靠人执行。现在：SOP 写成 Skill，靠 AI 执行。执行质量从「看人状态」变成「看 Skill 质量」。

PART 02 / 02

可迁移到 OpenClaw

  • Skill 不绑定平台：写好的 Skill 可以在 Claude Code、OpenClaw 等多个 Agent 环境中运行
  • 本地 → 远程：在本地验证好的 Skill，可以直接部署到 Mac Mini 上的 OpenClaw
  • 人工 → 自动：从「你触发 Skill」到「定时自动执行 Skill」
  • 个人 → 团队：好的 Skill 可以分享给团队，统一工作标准

Skill 是可迁移的能力资产。你投入的每一分钟，都在积累可复用的生产力。

PART 03

编写
方法论

先想清楚，再动手写

03
THREE STEPS

三步构建 Skill

1

梳理业务目标

你到底要解决什么问题？

2

明确方法论

你自己怎么做这件事？

3

定义输出物

要输出给你什么？

STEP 01

梳理自己的业务目标

  • 问自己：我到底要用 Skill 解决什么业务问题？
  • 要具体：不是"提高效率"，而是"每天节省 2 小时的竞品分析时间"
  • 要可衡量：写完 Skill 后，怎么判断它好不好用？
  • 要聚焦：一个 Skill 解决一个问题，别贪多

没有清晰业务目标的 Skill，写出来只是"能跑"，不是"好用"。

STEP 02

我自己的方法论是什么？

  • 先手动做一遍：你自己做这件事的完整流程是什么？
  • 提炼关键步骤：哪些步骤是必须的？哪些可以省略？
  • 固化判断标准：你做决策时依据什么？把它写进 Skill
  • 注入领域知识：你知道但 AI 不知道的"行业常识"

Skill 本质是你的方法论的编码。你不清楚，AI 也不会清楚。

STEP 03

要输出给我什么？

  • 格式要明确：Markdown 报告？Excel 表格？HTML 页面？
  • 结构要固定：每次产出的框架一致，方便对比和积累
  • 质量有标准：什么样的产出算"合格"？什么算"优秀"？
  • 落盘要自动：产出自动保存到指定位置，别丢在终端里

输出定义越精确，Skill 的一致性和可复用性越高。

PART 04

实操技巧

四个让产出质量翻倍的关键习惯

04
TIP 01

用最好的模型写

  • Skill 是一次性投入：写 Skill 的时候用最强模型，运行时可以降级
  • 理解力决定上限：强模型能更好地理解你的方法论和意图
  • 细节处理：边界情况、异常处理，强模型考虑得更周全

写 Skill 是投资行为，不要在投资阶段省成本。

TIP 02

用 Claude Code 的
Plan 模式

  • 先规划再执行：让 AI 先出方案，你审批后再动手
  • 降低返工率：在方向上达成一致，避免写完不满意推倒重来
  • 保留决策权：你是 reviewer，AI 是 executor

Plan 模式 = 在动手前先对齐预期，是质量保障的第一道关。

TIP 03

用实习生的思维

像带实习生一样管理 AI 的产出

👁

看执行过程

观察 AI 的思考路径和工具调用

📄

看产出结果

评估输出质量，标记好坏

📂

沉淀好的

结果 → references
脚本 → scripts

🔄

多次迭代

不断优化，逼近理想产出

TIP 04

本地 AI 工作区
学习 OpenClaw 架构

  • 参考成熟架构：OpenClaw 的目录结构和协作模式值得借鉴
  • 本地化适配：不是照搬，而是理解设计思路后融入自己的工作流
  • 持续演进：工作区架构不是一次性的，随着 Skill 增多要持续优化

好的架构让 Skill 之间可以协作，而不是孤立运行。

从单文件到专业级工程结构

05
PART 05 / 01

工程化目录结构

skill-name/
├── SKILL.md          ← 核心指令（必须）
├── references/       ← 参考资料（按需加载）
│   ├── guidelines.md
│   └── examples.md
├── scripts/          ← 可执行脚本
│   └── analyze.py
└── assets/           ← 模板和资源文件
    └── template.html

SKILL.md：核心

工作流程、判断标准、输出规范

references/：知识

行业数据、评估标准、最佳实践

scripts/：执行

数据处理、文件转换、API 调用

assets/：资源

输出模板、配置文件、素材

PART 05 / 02

工程化的好处

  • 关注点分离：指令归指令，数据归数据，脚本归脚本
  • 按需加载：大型参考资料不会撑爆上下文窗口
  • 独立迭代：改参考资料不用动核心逻辑，改脚本不用改指令
  • 可测试：脚本可以独立运行和调试，不依赖 AI

单文件 Skill 是笔记本，工程化 Skill 是生产线。当你的 Skill 超过 200 行，就该考虑拆分了。
